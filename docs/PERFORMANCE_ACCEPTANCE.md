# SJFX 真实 1 / 5 / 10 GiB 性能与恢复验收

本基线验证的是“真实文件、真实 IO、真实解析、可恢复、可核验”，不是把小文件的
`total_size` 字段改大后模拟 10 GiB。每次正式验收必须固定服务器、模型、解析模式和
代码版本，并保留原始数据集清单、机器信息及脚本生成的 JSON。

## 1. 先统一容量与覆盖口径

容量口径分成两层，不能混为一谈：

- **资料包总量**可以是数十至数百 GiB，由多个文件和目录组成；系统按批次、检查点和
  按需深入方式处理，不要求把全部正文同时放入内存或模型上下文。
- **单个内容对象上限**统一为 10 GiB，即普通源文件、压缩包容器、压缩包单成员、单个
  压缩包累计实际解压内容和一次导出原始内容都不得超过 `10737418240` 字节。组件配置
  可以主动调低，但不得高于这个硬上限。

固定 1 / 5 / 10 GiB 矩阵用于验证上述单项边界和渐进处理机制，不代表整个资料库只能有
10 GiB。对于数十或数百 GiB 总资料包，应额外执行“全包清点 + 分批分析 + 不超过
10 GiB 的选定范围导出”验收。

系统严格区分三类覆盖率：

| 覆盖对象 | JSON 字段 | 通过含义 |
| --- | --- | --- |
| 清点覆盖率 | `inventory_coverage` | 所有在约定扫描范围内的文件都已登记路径、类型和大小，且未命中截断、目录、节点、深度或读取错误 |
| 内容解析覆盖率 | `parse_coverage` | 每个已清点文件都进入完成、部分完成或明确失败状态；待处理数为 0，失败与截断原因可见 |
| 语义分析覆盖率 | `semantic_analysis_coverage` | 显示完整正文、有限投影和按需深挖各自数量；只有真正全文完成时才允许标记完整 |

“100% 清点”不等于“100% 全文深度分析”。数百 GiB 场景的正确承诺是 100% 清点、
所有文件进入可解释的终态，并通过有限语义投影快速给出概览；用户选中的范围再进行高精度
解析。只要扫描结果出现 `truncated=true`、读取错误或目录/节点/深度上限命中，本次清点
就必须判为不完整。安全上限可以配置，但不能通过隐藏截断来宣称完成。

清点基数包含扫描根下所有普通文件和目录，包括隐藏项、敏感扩展名和解析器不支持的格式；
后两类可以只登记元数据并禁止内容解析，但不能从清单消失。符号链接不跟随并单独计数。
验收工具的独立遍历不复用扫描器忽略规则，避免双方同时漏掉同一文件后产生假 100%。

## 2. 验收前置条件

1. 使用专用本地状态和解析临时目录，不使用容量较小的系统 `/tmp`：

   ```env
   SJFX_STATE_DIR=/var/lib/sjfx-data-analysis-agent
   SJFX_PARSE_TEMP_DIR=/var/tmp/sjfx-data-analysis-agent-parse
   PARSE_TEMP_DISK_RESERVE_BYTES=1073741824
   ```

2. 临时卷至少能容纳“待展开内容 + 1 GiB 保留空间”，导出卷至少能容纳“原始选中内容
   + ZIP 开销 + 1 GiB 保留空间”。开始前、结束后剩余空间均不得低于 20%。
3. 普通文件、压缩包容器、成员、累计解压量和导出上限均应为 10 GiB；成员数、压缩比、
   成员路径深度等防压缩炸弹限制仍必须启用。
4. 根据样本文件数调整 `MAX_SCAN_FILES`、`MAX_SCAN_DIRECTORIES`、`MAX_SCAN_NODES`、
   `MAX_SCAN_DEPTH` 和 `MAX_SCAN_ENTRIES_PER_DIRECTORY`，同时保留合理安全边界。验收结果中
   不得出现任何上限命中。
5. 本地 Ollama 只监听回环地址。正式对比时固定模型、模型哈希、CPU/GPU、Docling/OCR
   版本和 `.env` 配置。

## 3. 真实测试矩阵

分别准备约 1、5、10 GiB 的真实混合数据包。`--expected-size-gib` 按二进制 GiB 校验，
默认允许上下 10% 偏差；10 GiB 档若需要完整导出，真实原始内容必须不超过 10 GiB
导出硬上限。

每档至少包含：

- PDF、DOCX、XLSX、PPTX、CSV/JSON、图片、TXT/Markdown、ZIP/TAR；
- 可复制文本 PDF 和扫描型 PDF；
- 正常文件、已知损坏文件、加密 ZIP、超限压缩比或不支持成员；
- 精确重复副本和近似版本；
- GB18030 文本、大表、深层目录和单目录大量文件；
- 至少两个字段结构相同的 CSV/XLSX，例如两个月销售表，用于验证跨文件合计、加权平均、
  最大/最小和总行数；另放一个同名字段但结构不同的表，验证系统拒绝静默混算。

禁止使用以下方式冒充真实负载：

- 修改扫描结果或测试对象中的 `total_size`、`size` 字段；
- 使用 `truncate`、文件 seek 空洞或文件系统稀疏属性生成看似 1/5/10 GiB 的文件；
- 只复制一个极小文件并重复引用其路径；
- 只验证目录扫描而跳过实际解析、检索、恢复和导出。

稀疏文件只能用于容量边界的单项开发测试，不能进入正式性能结果。验收脚本会通过独立
`stat` 遍历复算真实字节，并在操作系统提供分配块信息时拒绝稀疏样本。

## 4. 自动验收阶段

`scripts/benchmark_package.py` 的 `acceptance` 模式依次执行：

1. `independent_measurement`：独立遍历真实目录，记录逻辑字节、已分配字节、格式和稀疏文件；
2. `inventory`：调用产品扫描器，并与独立结果逐项核对，要求文件数和字节数完全一致；
3. `analysis`：调用真实分批分析流水线，生成检查点、三类覆盖率和持久化证据索引；
4. `retrieval`：对同一个问题连续检索两次，要求都使用持久化证据索引且证据顺序一致；
5. `recovery`：重新打开状态库并用全新解析器实例进入同一任务，验证文件哈希/解析契约检查点
   被复用、没有文件回到待处理状态；
6. `export`：导出整个固定档资料包，重新读取导出文件并计算 SHA-256；
7. 输出一个 `sjfx-performance/2.0` JSON，逐条列出 required check 的 pass/fail。

`recovery` 自动钩子验证的是确定性检查点重入。正式交付还必须补做一次真实 Worker 故障演练：
分析进行中正常终止 Worker 进程，确认 Web 仍可查询任务；超过失联阈值后重新启动 Worker，
确认任务继续而不是从头解析，已完成文件的内容哈希和检查点保持不变。把相关任务状态、日志
时间点和恢复耗时作为 JSON 的外部附件保存。

## 5. 正式执行命令

先为基准状态、解析临时文件和导出准备专用本地卷。例如：

```bash
mkdir -p /var/tmp/sjfx-benchmark/work /var/tmp/sjfx-benchmark/export
```

然后执行固定矩阵：

```bash
python scripts/benchmark_package.py /data/benchmark/1gib \
  --expected-size-gib 1 --label 1GiB --profile acceptance --mode fast \
  --work-dir /var/tmp/sjfx-benchmark/work --export-dir /var/tmp/sjfx-benchmark/export/1gib

python scripts/benchmark_package.py /data/benchmark/5gib \
  --expected-size-gib 5 --label 5GiB --profile acceptance --mode fast \
  --work-dir /var/tmp/sjfx-benchmark/work --export-dir /var/tmp/sjfx-benchmark/export/5gib

python scripts/benchmark_package.py /data/benchmark/10gib \
  --expected-size-gib 10 --label 10GiB --profile acceptance --mode fast \
  --ten-gib-boundary-kind archive \
  --work-dir /var/tmp/sjfx-benchmark/work --export-dir /var/tmp/sjfx-benchmark/export/10gib
```

10 GiB 档必须含一个恰好 10 GiB 的单对象边界样本；上例使用归档文件。若边界样本是普通文件，
将 `archive` 改为 `regular`。验收结果会记录该对象的实测字节、路径和最终解析状态。该对象与
其他小型混合格式样本相加会略高于 10 GiB，因此这一档导出并复算边界对象本身；1/5 GiB 档
仍导出完整根目录，避免用一个必然超过产品单次导出硬上限的范围制造假失败。

大包首轮应使用 `fast`，这是“全量清点 + 有界概览”的生产路径。随后从 10 GiB 档选取固定
PDF、Office、大表和主题范围，用页面的“重新分析当前范围”执行 `accurate` 深挖，记录高精度
解析耗时、覆盖变化和证据变化，不能把首轮有限投影写成全文分析。

只想先验证工具和本机依赖时可以使用 `--profile smoke`；它仍会真实执行清点和分析，但检索、
恢复、导出钩子不是必需项，因此其 JSON 不能作为完整交付验收结果。

结果默认写入 `outputs/benchmarks/`。进程退出码含义：`0` 为全部必需检查通过，`2` 为流水线
完成但至少一个阈值失败，`1` 为运行异常，`130` 为人工中止。无论成功与否都应保留 JSON。

## 6. 自动记录的指标与门槛

脚本至少记录：

- 输入：独立测得的真实字节、文件数、目录数、格式、最大文件、稀疏文件；
- 阶段：清点、分析、两次检索、检查点重入、导出和端到端耗时；
- 资源：Linux 使用 `/proc` 采样基准进程树 CPU/RSS/进程数，其他平台在标准库能力不足时
  明确写入测量局限；
- 磁盘：输入、工作、专用解析临时目录、结果和导出卷的前后容量及增量；
- 覆盖：清点、内容解析、语义分析三类对象，以及失败、待处理、抽样、截断和压缩成员统计；
- 恢复：检查点复用数、恢复前后终态数和恢复后待处理数；
- 导出：ZIP 路径、实际字节数和重新计算的 SHA-256；
- 判定：每个阈值的实际值、期望值、是否必需、是否通过。

默认硬门槛：

| 检查项 | 1 GiB | 5 GiB | 10 GiB |
| --- | ---: | ---: | ---: |
| 独立实测容量符合档位 | ±10% | ±10% | ±10%，且完整导出原始内容不超过 10 GiB |
| 稀疏样本 | 0 | 0 | 0 |
| 清点覆盖率 | 100% | 100% | 100% |
| 分析待处理文件 | 0 | 0 | 0 |
| 三类覆盖对象 | 全部存在 | 全部存在 | 全部存在 |
| 两次持久化检索 | 结果稳定 | 结果稳定 | 结果稳定 |
| 检查点重入 | 通过 | 通过 | 通过 |
| 导出及重算 SHA-256 | 通过 | 通过 | 通过 |
| 进程树 RSS 峰值 | 不高于物理内存 70% | 同左 | 同左 |
| 验收后磁盘剩余 | 不低于 20% | 同左 | 同左 |

已知损坏、加密或故意越界文件可以进入明确的 `failed`/`partial` 终态，但原因必须可见，不能
让其他文件失败，也不能仍显示“全文完整”。健康样本子集应另外达到 100% 解析成功。

端到端耗时受文件数量、扫描 PDF 页数、OCR、复杂表格和模型 Token 数影响，默认不设置一个
只按 GiB 推导的秒数。项目交付方应根据目标硬件用 `--max-inventory-seconds`、
`--max-analysis-seconds`、`--max-end-to-end-seconds` 固化自己的门槛，并分别报告纯文本/Office、
普通 PDF、扫描 PDF 三组 P50/P95。

## 7. 仍需人工核对的功能结果

- 原始目录按节点分页加载，首次响应不能携带全量树；展开后文件总数仍与清点一致。
- 分析过程中能先看到首版概览和当前三类覆盖率，刷新页面后进度不丢失。
- 两个同构销售表的合计等于两表之和，平均值按有效数加权；结构不同的同名字段必须拒绝混算。
- 每个重要结论可回到文件、页码/工作表/行范围或压缩成员；无证据正式结论数为 0。
- 加密压缩成员只影响自身并带原因，目录穿越、超压缩比、超成员数和超路径深度被阻止。
- 选中范围超过 10 GiB 时导出应在读取全部源文件前安全拒绝，不留下伪完整 ZIP；失败的
  `.part` 文件可被清理。

只有自动 JSON 全部 required checks 通过、真实 Worker 恢复演练通过、上述人工功能核对通过，
才能把对应版本标记为“V1–V3 验收通过”。
