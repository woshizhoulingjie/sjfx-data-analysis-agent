# SJFX 数据分析 Agent 运行与恢复说明

## 当前架构

项目采用离线单机模块化单体：FastAPI 只负责提交任务、查询状态和返回结果；SQLite WAL 保存任务、进度、心跳、检查点和结果；独立 `worker.py` 负责扫描、解析、模型调用、报告和大文件导出。

本机 Ollama 是共享 GPU 服务，项目 Worker 默认单实例、单任务运行。项目不会启动、停止或修改 Ollama。

容量口径：整个资料包可以由数十/数百 GiB 文件组成；普通单文件、归档容器、归档单成员、
单归档累计实际解压内容和一次导出原始内容统一限制为 10 GiB。系统承诺在未触发安全上限时
100% 清点，内容解析与语义深度则分别报告，不能用一个“完成”状态混淆。

## 启动

在项目根目录分别启动 Web 和 Worker：

```bash
mkdir -p logs
nohup .venv/bin/python -u app.py </dev/null >> logs/app.log 2>&1 &
nohup .venv/bin/python -u worker.py </dev/null >> logs/worker.log 2>&1 &
```

如果使用 systemd，可将 `deploy/sjfx-web.service.example` 和 `deploy/sjfx-worker.service.example` 复制为本机服务文件后再由管理员启用。不要在没有确认权限和现有进程的情况下直接执行 `systemctl`。

生产启动前至少确认以下目录和身份配置：

```env
SJFX_STATE_DIR=/var/lib/sjfx-data-analysis-agent
SJFX_PARSE_TEMP_DIR=/var/tmp/sjfx-data-analysis-agent-parse
PARSE_TEMP_DISK_RESERVE_BYTES=1073741824
SJFX_OWNER_ID=primary
MAX_CONTENT_BYTES=10737418240
```

SQLite/WAL 和解析临时项应在专用本地卷，不放在 NFS 或容量较小的系统 `/tmp`。轮换
`SJFX_API_ACCESS_TOKEN` 时保持 `SJFX_OWNER_ID` 不变；改变 owner 前先备份并执行数据迁移。

## 任务流程

- `POST /api/scan` 返回 `202` 和 `job_id`，Worker 异步完成扫描、解析、主题目录和概览。
- `GET /api/scan/<scan_id>` 和 `GET /api/analysis/<scan_id>` 默认返回有界概览、首屏树和当前
  渐进状态；`?full=1` 只用于受控诊断兼容，不供大包前端日常调用。
- `GET /api/tree/<scan_id>?kind=physical|analysis&node_key=...&offset=...&limit=...` 按节点分页读取目录。
- `GET /api/summaries/<scan_id>?offset=...&limit=...` 独立分页读取摘要。
- `POST /api/report` 返回 `202`，Worker 生成 Word 概览。
- `POST /api/export` 返回 `202`，Worker 生成去重后的待整编包、统一交接说明、覆盖清单和结论—证据链。
- `POST /api/download-ticket` 用已认证会话换取绑定当前 owner 和文件名的一次性短期票据；浏览器
  随后通过普通下载导航让响应直接流式落盘，不在页面内把最多 10 GiB 的成果缓冲成 Blob。
- `GET /api/jobs/<job_id>` 查询 `queued/running/completed/failed/cancelled` 状态。
- `GET /api/jobs?status=active` 查询当前用户的运行、排队和取消中任务。
- `POST /api/jobs/<job_id>/cancel` 取消任务。排队任务立即结束；运行任务先协作清理解析资源，随后由 Worker 监管进程强制收尾。

任务中心会显示队列位置、前序阻塞任务、当前文件、运行时长和 Worker 心跳。页面刷新或短暂断网不会中止后台任务，恢复连接后会自动继续同步。

扫描完成后先持久化清点概览；分析批次运行期间持续保存阶段、进度、首版概览和三类覆盖率。
前端无需等完整主题树生成后才第一次看到有效结果。目录树和摘要按页加载，分页数量不能代替
清点总数，是否 100% 以 `inventory_coverage.complete` 以及所有扫描限制计数为准。

## 失联恢复

SQLite 任务表记录 Worker 心跳。每个任务在独立、可终止的监管子进程中运行，父 Worker 即使正在等待 NAS、Docling 或 Ollama，也会按 `WORKER_HEARTBEAT_SECONDS` 独立刷新心跳。Worker 启动时只会把超过 `WORKER_STALE_SECONDS` 没有心跳的运行任务重新排队；健康运行任务不会被抢走。处于取消状态但 Worker 失联的任务会安全标记为已取消。

扫描、分析、摘要、报告和导出各有独立的总运行时限。默认值可通过 `JOB_SCAN_TIMEOUT_SECONDS`、`JOB_ANALYSIS_TIMEOUT_SECONDS`、`JOB_SUMMARY_TIMEOUT_SECONDS`、`JOB_DOCUMENT_SUMMARY_TIMEOUT_SECONDS`、`JOB_REPORT_TIMEOUT_SECONDS` 和 `JOB_EXPORT_TIMEOUT_SECONDS` 调整。

`data/worker.lock` 是项目 Worker 单实例锁。第二个 Worker 会拒绝启动，以防多个本地模型调用同时挤占共享 GPU。

长扫描/分析达到单次监管时间片时，可以在未超过 `MAX_JOB_RESUME_ATTEMPTS` 的前提下重新排队，
新进程会校验源文件 SHA-256、解析模式和解析契约后复用检查点。仅大小/mtime 相同不足以复用。
解析超时、取消或崩溃后，父进程负责回收当前任务拥有的临时目录；启动和周期清理只删除匹配
项目命名规则且超过 `PARSE_TEMP_STALE_SECONDS` 的陈旧项。

## 验证

```bash
.venv/bin/python -m py_compile app.py worker.py config.py services/*.py
.venv/bin/python -m unittest discover -s tests -v
curl -sS http://127.0.0.1:18000/api/status
```

提交扫描后应先看到 HTTP `202`，再通过任务接口轮询；不要把同步 HTTP 是否立即返回文件作为成功标准。

发布前还需用真实分配在磁盘上的 1/5/10 GiB 混合样本执行：

```bash
python scripts/benchmark_package.py /data/benchmark/10gib \
  --expected-size-gib 10 --label 10GiB --profile acceptance --mode fast \
  --ten-gib-boundary-kind archive \
  --work-dir /var/tmp/sjfx-benchmark/work \
  --export-dir /var/tmp/sjfx-benchmark/export/10gib
```

脚本独立复算实际字节，拒绝稀疏样本，记录清点/分析、进程树 CPU/RSS、磁盘前后、两次检索、
检查点重入、导出 SHA-256 和逐项 pass/fail。完整矩阵和真实 Worker 停止/恢复演练见
`docs/PERFORMANCE_ACCEPTANCE.md`。

## 安全边界

- 默认使用本机 Ollama，文档正文全程在服务器本地处理。
- 本地模型生成由 `ENABLE_SHARED_OLLAMA` 控制，不需要前端确认。
- 非回环 `HOST` 必须显式配置最小范围 `SCAN_ALLOWED_ROOTS`，否则启动失败；不要授权整个 `/home`
  或文件系统根目录。
- `SCAN_IGNORED_DIRS`/`SCAN_IGNORED_FILES` 默认空；显式排除项命中时会令清点覆盖不完整。
- 浏览器 Token 只保存在当前标签的 `sessionStorage`，关闭标签后不长期保留。
- 下载票据默认 120 秒、仅可消费一次，且不能换文件或跨 owner 使用；失败或中断后由用户重新
  点击下载取得新票据，不复用旧 URL。
- 扫描登记符号链接自身但不跟随目标，并有最大文件、目录、节点、单目录条目、深度和取消检查；任何上限
  命中都明确标记清点不完整。
- 归档在 `SJFX_PARSE_TEMP_DIR` 逐成员处理，同时限制 10 GiB 单项容量、成员数、压缩比、
  路径深度和剩余空间；加密成员失败不应拖垮整个归档任务。
- 原始目录、主题目录和摘要均使用有界分页接口，避免超大 JSON 和浏览器一次创建全量节点。
- 日志使用轮转并过滤常见密钥字段；不得记录原始提示词、全文正文、认证头或完整敏感路径。
