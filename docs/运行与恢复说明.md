# SJFX 数据分析 Agent 运行与恢复说明

## 当前架构

项目采用离线单机模块化单体：Flask 只负责提交任务、查询状态和返回结果；SQLite WAL 保存任务、进度、心跳、检查点和结果；独立 `worker.py` 负责扫描、解析、模型调用、报告和大文件导出。

本机 Ollama 是共享 GPU 服务，项目 Worker 默认单实例、单任务运行。项目不会启动、停止或修改 Ollama。

## 启动

在项目根目录分别启动 Web 和 Worker：

```bash
nohup .venv/bin/python -u app.py </dev/null > .logs/flask-18000.log 2>&1 &
nohup .venv/bin/python -u worker.py </dev/null > .logs/worker.log 2>&1 &
```

如果使用 systemd，可将 `deploy/sjfx-web.service.example` 和 `deploy/sjfx-worker.service.example` 复制为本机服务文件后再由管理员启用。不要在没有确认权限和现有进程的情况下直接执行 `systemctl`。

## 任务流程

- `POST /api/scan` 返回 `202` 和 `job_id`，Worker 异步完成扫描、解析、主题目录和概览。
- `POST /api/report` 返回 `202`，Worker 生成 Word 概览。
- `POST /api/export` 返回 `202`，Worker 生成去重后的待整编包、统一交接说明、覆盖清单和结论—证据链。
- `GET /api/jobs/<job_id>` 查询 `queued/running/completed/failed/cancelled` 状态。
- `POST /api/jobs/<job_id>/cancel` 请求协作取消。扫描、解析和导出会在安全检查点停止。

## 失联恢复

SQLite 任务表记录 Worker 心跳。Worker 启动时只会把超过 `WORKER_STALE_SECONDS` 没有心跳的运行任务重新排队；健康运行任务不会被抢走。处于取消状态但 Worker 失联的任务会安全标记为已取消。

`data/worker.lock` 是项目 Worker 单实例锁。第二个 Worker 会拒绝启动，以防多个本地模型调用同时挤占共享 GPU。

## 验证

```bash
.venv/bin/python -m py_compile app.py worker.py config.py services/*.py
.venv/bin/python -m unittest discover -s tests -v
curl -sS http://127.0.0.1:18000/api/status
```

提交扫描后应先看到 HTTP `202`，再通过任务接口轮询；不要把同步 HTTP 是否立即返回文件作为成功标准。

## 安全边界

- 默认使用本机 Ollama，不向云端发送文档正文。
- 云端 DeepSeek 必须显式开启并经前端确认。
- 扫描不跟随符号链接，并有最大目录深度、最大文件数和取消检查。
- 日志使用轮转并过滤常见密钥字段；不得记录原始提示词、全文正文、认证头或完整敏感路径。
