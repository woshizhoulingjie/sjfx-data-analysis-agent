# SJFX 数据分析 Agent：系统架构与邮件关系挖掘详解

> 本文是一份可以单独发给新成员阅读的项目说明。它解释系统为什么这样设计、一次数据导入如何流转、代码各层负责什么、几千份邮件怎样做关系挖掘，以及当前版本做到哪里、后续怎样继续扩展。

## 1. 项目定位

SJFX 不是“上传文件后让大模型写一段总结”的脚本，而是一套面向调查、研判和资料整理的本地数据分析系统。它的核心任务是把一批原始文件变成四类可以继续使用的资产：

1. **目录资产**：知道数据包有哪些文件、目录、压缩包成员、类型、大小和结构。
2. **证据资产**：每个事实都能回到原始文件、页码、段落、表格或字符范围。
3. **分析资产**：文件摘要、节点摘要、主题、实体、事项、关系图和情报概览。
4. **过程资产**：任务状态、进度、检查点、失败原因、暂停位置和可恢复队列。

这四类资产缺一不可。只有摘要没有证据，结果无法审查；只有解析没有过程状态，大数据包中断后就只能从头开始；只有关系图没有来源，图上的连接不能用于正式研判。

## 2. 用户真正要完成的工作

一个典型用户并不是只想看一段总摘要，而是希望完成下面的闭环：

```text
导入资料包
  → 了解资料范围
  → 选择优先文件
  → 先看初步结果
  → 决定是否深挖
  → 补充剩余文件
  → 查询人物/机构/事项/时间线
  → 检查原文证据
  → 输出正式报告
```

因此系统必须允许用户在任何阶段做控制：暂停当前处理、继续处理、结束本次运行、切换到另一个数据包、回到选择页、补充剩余文件、重新生成报告。已完成的文件和证据不能因为一次新的选择而被清空。

## 3. 总体架构

```text
┌──────────────────────────────────────────────┐
│ 浏览器：HTML / CSS / 原生 JavaScript          │
│ 普通导入页、大数据包页、目录、概览、证据页     │
└──────────────────────┬───────────────────────┘
                       │ HTTP/JSON
┌──────────────────────▼───────────────────────┐
│ app.py + web_compat.py                         │
│ FastAPI、认证、目录 API、任务编排、报告下载     │
└──────────────────────┬───────────────────────┘
                       │ 事务读写
┌──────────────────────▼───────────────────────┐
│ SQLite WAL                                     │
│ 任务队列、文件状态、检查点、摘要、证据、关系图   │
└───────────────┬──────────────────┬────────────┘
                │                  │
┌───────────────▼─────────┐  ┌────▼────────────────┐
│ worker.py                │  │ large_package_worker │
│ 普通任务 Worker           │  │ 大数据包 Worker      │
└───────────────┬─────────┘  └────┬────────────────┘
                └──────────┬──────┘
                           ▼
┌──────────────────────────────────────────────┐
│ 解析、证据、摘要、关系和报告服务               │
│ UnifiedParser / Docling / OCR / vLLM / 统计算法 │
└──────────────────────────────────────────────┘
```

### 3.1 Web 层

`app.py` 是应用入口，`web_compat.py` 提供 FastAPI 和历史同步处理器之间的兼容边界。Web 层的职责是：

- 接收数据包路径、选择范围和用户操作。
- 扫描目录并返回可选择的文件清单。
- 创建普通任务或大数据包任务。
- 读取任务状态并返回给前端。
- 处理暂停、继续、停止、补充和切换数据包。
- 组织摘要、概览和报告生成。
- 下载 JSON、Word 和证据包。

Web 层不应该自己长时间解析文件。否则浏览器请求会被占住，服务重启也会导致任务丢失。

### 3.2 普通 Worker

`worker.py` 是普通任务的执行器。它从持久化队列领取任务，再把当前任务放到受监督的子进程中运行。父 Worker 负责：

- 领取任务和增加尝试次数。
- 定期写入心跳。
- 检查用户是否取消。
- 对超过运行时限的任务停止子进程。
- 将带检查点的任务重新排队。
- 在任务完成后推进下一阶段。
- 对短暂 SQLite 锁冲突自动重试。

这种父子进程结构可以保证单个解析器、OCR 或模型调用卡住时，Worker 本身仍然可用。

### 3.3 大数据包 Worker

`large_package_worker.py` 专门处理大数据包。它与普通队列隔离，避免几千个文件的任务阻塞普通导入。大包任务包含：

- `inventory`：生成全量清单。
- `quick`：快速解析和元数据提取。
- `deep`：按用户选择做深度解析。
- `summary`：生成文件、节点和跨文件摘要。
- `report`：生成情报概览及导出文件。

### 3.4 状态和数据层

`services/storage.py` 是所有进程共享的唯一状态边界。重要信息不会只放在浏览器内存中，而是写进数据库：

- `analysis_jobs`：普通任务队列。
- 导入任务：当前阶段、选择版本、检查点和恢复信息。
- 文件状态：待处理、处理中、完成、部分完成、失败、等待重试。
- 摘要状态：初步摘要和深度摘要分开保存。
- 证据索引：来源文件和定位信息。
- 关系图：节点、边、关系类型、置信度和证据。
- 大包专用任务、文件队列和报告状态。

SQLite 使用 WAL 模式。长任务不依赖一个大事务，而是按文件和批次提交结果。

## 4. 普通导入的完整流程

### 4.1 扫描阶段

用户提交一个目录后，系统递归扫描目录，形成稳定的 inventory。每个文件至少记录：

- 相对路径和显示名称。
- 文件类型、大小和修改时间。
- 内容或源文件 SHA-256。
- 所属目录节点。
- 是否为压缩包、压缩包成员或可解析文件。
- 扫描错误和忽略原因。

扫描阶段不调用大模型。这样用户可以先看到数据范围，再决定分析哪些内容。

### 4.2 选择阶段

前端按文件名、目录、类型、大小和状态筛选清单。用户可以只选择 20 个文件，也可以选择全部文件。未选文件不会被删除，它们会留在 inventory 中，之后可以通过“只看待补充文件”重新选择。

选择会保存版本号和选中路径。版本号用于防止页面过期时覆盖别人的新选择。

### 4.3 解析阶段

`services/unified_parser.py` 将不同格式统一为内部文档对象。常见格式使用专门解析器：

- PDF：pypdf、Docling。
- DOCX：python-docx、Docling。
- PPTX：python-pptx、Docling。
- XLSX/CSV：openpyxl、pandas。
- 图片或扫描 PDF：RapidOCR/Docling。
- HTML/Markdown/TXT/JSON：文本和结构化解析。
- ZIP/TAR：安全枚举成员，并为成员建立逻辑路径。

解析结果会保存完整文本、结构、页/段落/表格位置、附件和解析错误。原文件不被改写。

### 4.4 初步摘要阶段

初步摘要的目标是让用户快速了解资料，而不是一次性得到最终结论。流程通常为：

```text
文件初步摘要 → 节点初步摘要 → 初步情报概览
```

初步摘要使用受控长度的文档片段，输出文件主题、参与者、事项、关键事实、待核实问题和证据引用。多个文件通过批次任务处理，避免一个大请求超过模型上下文。

### 4.5 深度摘要阶段

用户确认需要深挖后，系统对选中文件进行深度解析和摘要。深度结果与初步结果分开保存，可以比较两个阶段的差异。后台深度回填会让位于新的前台导入，保证用户当前操作优先。

### 4.6 概览和报告阶段

报告生成器读取已完成的结构化摘要、证据和关系图，生成：

- 解析版目录。
- 正式智能目录。
- 情报概览。
- 推荐研究方向。
- JSON 机器可读结果。
- Word 报告。
- 包含证据引用的 ZIP。

正式报告不会把未完成的深度结果冒充为已完成结论。

## 5. 普通任务的暂停、继续和补充

### 暂停

暂停操作会：

1. 记录暂停前的导入状态。
2. 将运行中的任务标记为取消中。
3. 不再领取新的文件。
4. 保留已经提交的解析、摘要和证据。
5. 将任务显示为可继续状态。

### 继续

继续操作会读取检查点：

1. 恢复暂停前阶段。
2. 检查每个子任务的真实状态。
3. 保留 completed 子任务。
4. 只为 failed、cancelled、cancelling 或不存在的任务重建队列。
5. 让状态机继续推进节点摘要和概览。

### 补充文件

补充文件不会重新创建整个数据包。系统将新选择与已经处理的路径合并，新增文件进入相同的解析和摘要链，旧结果继续可用。这是“先处理 20 个，之后回来处理剩余 10 个”的实现基础。

### 切换数据包

切换数据包时，前端会解绑旧任务的轮询器，然后加载新数据包。后端任务仍然保留在数据库中，用户稍后可以从历史数据包继续。这样旧任务的延迟响应不会覆盖新页面。

## 6. 大数据包的设计

大包最重要的原则是把“看清全局”和“深挖重点”分开：

```text
全量 inventory
  → 全量 quick parse
  → 用户按清单选择深度范围
  → 深度解析选中文件
  → 文件和节点摘要
  → 情报概览和报告
```

快速阶段让用户知道所有文件是否可读、哪些文件值得关注。深度阶段只消耗用户选择的范围。文件状态和队列状态必须同时更新；如果文件重选，原来 completed 的队列行会被恢复为 queued，防止出现界面显示待处理但 Worker 找不到任务的情况。

## 7. 邮件关系挖掘

### 7.1 当前输入

邮件分析主要面向 `.eml`、`.msg`、`.mbox` 等邮件或具有相似字段结构的文档。系统会抽取：

- 日期。
- 发件人、收件人、抄送、密送、Reply-To。
- Subject。
- Message-ID、In-Reply-To、References。
- 文号、事项号、项目号、合同号。
- 附件名称和附件数量。
- 邮箱、电话、IP、URL、案件号等实体。
- 正文摘要、动作类型和语言信息。

每封邮件形成一条规范化记录，同时保留原始路径和哈希。

### 7.2 关系生成顺序

关系生成在 `services/homogeneous_documents.py` 中完成，顺序是从强证据到弱证据：

1. **回复关系**：`In-Reply-To` 精确命中另一封邮件的 `Message-ID`，建立 `reply_to`。
2. **引用关系**：`References` 头或正文中的明确文号，建立 `references`。
3. **同事项关系**：事项号、项目号或合同号完全一致，建立 `same_matter`。
4. **通信流程**：结合发件人/收件人方向、主题变体和日期，识别回复、追问、审批、通知和补充。
5. **共享实体**：两封邮件共同出现邮箱、电话、IP、URL 或案件号时建立候选边。
6. **证据保存**：每条边写入来源文件、目标文件、关系类型、置信度、理由和证据片段。

系统不会因为两封邮件出现同一个姓名就直接断定二者存在确定关系。弱信号会标记为 `candidate` 或 `derived`，等待模型或人工复核。

### 7.3 关系可信度

| 关系 | 证据 | 典型状态 |
| --- | --- | --- |
| `reply_to` | In-Reply-To 与 Message-ID 精确匹配 | validated |
| `references` | References 头或正文明确引用 | validated |
| `same_matter` | 事项号/合同号完全一致 | validated |
| `correspondence_flow` | 多项方向、主题和时间特征 | candidate/derived |
| `shared_entity` | 实体出现且有正文证据 | candidate/derived |

一条边的证据对象包含来源路径、目标路径、证据类型、片段和定位。关系图因此既可以用于探索，也可以回到原文核验。

### 7.4 几千份邮件的正确处理方式

几千份邮件不能组成一个模型请求。建议分成五类批次：

```text
批次 A：解析邮件头、正文和附件元数据
批次 B：提取实体、身份线索和附件指纹
批次 C：按 Message-ID、事项号和文号建立强关系
批次 D：按主题、参与者和时间恢复缺失的线程
批次 E：只对关键线程做深度摘要、时间线和调查报告
```

每个批次都写检查点。批次失败时只重做未完成部分。关系构建使用倒排索引，而不是对所有邮件做无界两两比较。当前保护阈值是：最多 50,000 条派生关系、每个源文件最多 500 条边、主题候选比较最多 200,000 对。这些阈值保护内存和查询性能，不限制原始邮件数量，也不会删除原文记录。

### 7.5 当前能回答的问题

当前版本可以较可靠地回答：

- 某封邮件回复了哪封邮件。
- 哪些邮件引用了同一份文件或事项。
- 某个事项的邮件按时间如何串联。
- 谁和谁之间有直接通信。
- 哪些实体在多个邮件或事项中出现。
- 哪些关系是明确证据，哪些只是候选线索。

### 7.6 仍需增强的问题

如果目标是调查级别的深挖，还应继续开发：

- 同一人的多邮箱、别名、签名和转发地址的实体消歧。
- 缺少 Message-ID 时的线程聚类。
- 邮件与附件、附件与独立文件之间的哈希和内容关联。
- 从正文抽取事件、动作、截止日期并生成时间线。
- 通信网络中的中心节点、桥接节点、密集群组和沉默期分析。
- 关系确认、排除、批注和审计日志。
- 支持按人物、机构、事项、时间窗口和关系类型切片查询。

## 8. 模型、统计和证据怎样协作

系统采用“确定性处理先行，模型解释随后”的方式：

```text
扫描 / 哈希 / 格式解析 / 字段抽取 / 去重
        ↓
证据索引和关系候选
        ↓
模型摘要、主题归纳、概览和研究方向
        ↓
证据校验、置信度分级和报告导出
```

模型主要负责语言理解和归纳，不负责替换来源证据。统计和相似度算法用于聚类、主题相似、结构化字段汇总和候选排序。正式结论必须能回指证据。

## 9. 主要技术栈

| 组件 | 技术 | 作用 |
| --- | --- | --- |
| API | FastAPI、Uvicorn、Jinja2 | HTTP、页面、任务控制 |
| 兼容层 | `web_compat.py` | 让历史同步处理器逐步迁移到 ASGI |
| 解析 | Docling、RapidOCR、pypdf、python-docx、python-pptx、openpyxl、pandas | 多格式文本和结构提取 |
| 邮件 | Python email 生态、字段规则、实体正则 | 邮件头、正文和实体抽取 |
| 模型 | vLLM，本地 Ollama 兼容路径 | 摘要、概览、研究方向 |
| 统计 | NumPy、scikit-learn | 相似度、聚类、统计 |
| 持久化 | SQLite WAL | 队列、检查点、结果和证据 |
| 导出 | python-docx、JSON、ZIP | 报告和证据包 |
| 前端 | 原生 JavaScript、HTML、CSS | 选择、轮询、暂停、补充和切换 |

## 10. 代码阅读顺序

1. `app.py`：API 路由、阶段编排、摘要和报告入口。
2. `services/storage.py`：任务表、队列、检查点和事务。
3. `worker.py`：领取、监督、超时、取消、重试和阶段推进。
4. `services/unified_parser.py`：多格式统一解析。
5. `services/package_analysis.py`：普通数据包解析。
6. `services/large_package_isolated.py` 与 `large_package_worker.py`：大包隔离队列。
7. `services/evidence.py`：证据选择和校验。
8. `services/homogeneous_documents.py`：邮件字段、实体和关系。
9. `services/reporting.py`、`services/exporter.py`：概览和导出。
10. `static/app.js`、`static/large-package.js`：前端状态和交互。

## 11. 部署和运行

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Web
python -u app.py

# 普通任务
python -u worker.py

# 大数据包任务
python -u large_package_worker.py
```

生产环境建议使用 `requirements.lock.txt`，并将以下内容放在环境变量或 `.env` 中：访问令牌、允许的数据根目录、模型服务地址、状态目录、解析临时目录和资源限制。原始邮件、数据库、模型权重、日志和报告不进入 Git。

## 13. 后续开发建议

### 第一阶段：调查级邮件基础

先做实体档案和附件联动。没有稳定身份，网络图会把同一个人拆成多个节点；没有附件联动，邮件正文中的关键证据可能无法进入同一条事项链。

### 第二阶段：线程和时间线

将邮件关系从“文件到文件”提升为“线程到事件”：同一线程形成时间线，每个事件包含发生时间、动作、参与者、来源和证据。

### 第三阶段：调查工作台

加入人工确认、关系排除、证据批注、收藏、标签和审计日志。系统应记录“谁在什么时候确认了哪条关系”，并允许重新计算而不覆盖人工结论。

### 第四阶段：大规模运行监控

增加每批处理吞吐、平均解析耗时、模型耗时、内存、GPU、失败率、重试次数和队列等待时间。几千份邮件能否稳定运行，最终取决于可观测性和增量重算能力，而不仅仅是模型大小。

## 14. 一句话理解整个项目

SJFX 的核心不是让模型“猜出一个答案”，而是把海量原始资料拆成可恢复的处理批次，把每个结论绑定到证据，把强关系和弱线索分开，再让用户可以反复补充、暂停、切换、复核和导出。
