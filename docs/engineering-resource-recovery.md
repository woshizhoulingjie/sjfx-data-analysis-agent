# 大包问答：资源不足暂停与恢复

## 范围与不变量

本阶段只增强大包资料问答后台及其原文入库。没有更换模型，没有减少文件、原文字符预算、段落、摘要或证据，没有更改敏感权限、前台、翻译、保护、普通包和大包主解析服务。不是100GB全链路容量验证。

## 问题及实现

- 旧实现先打开/创建包索引，再检查磁盘；构造异常在包级保护之外，可能中断其他包。现在先检查索引磁盘，再进入包级保护内初始化。坏包错误仍可见，其他包继续。
- 原文解析前另检查解析结果和实际解析临时目录（尊重 `SJFX_PARSE_TEMP_DIR`）。保留原1GiB余量；暂停后达到1.25GiB才恢复，避免临界值附近反复启动。这不是对整个数据包空间充足的保证。
- 识别结构化 `ENOSPC/EDQUOT/ENOMEM/EMFILE/ENFILE/MemoryError` 和 SQLite BUSY/LOCKED/NOMEM/FULL。跨子进程传递资源错误类型，不再变成普通坏文件错误。不能通过错误文本猜测分类。
- 写原文时资源错误不再被“坏段落跳过”分支吞掉：回滚删除及新增段落、全文索引、文档状态和版本。保留既有证据；待处理文件继续pending，资源恢复后自动重试。
- 每包资源重试间隔30秒，使用单调时间；状态含中文原因、资源类型、容量详情、预计重试时间。所有当前包都暂停时心跳为 `waiting_for_resources`，不能报成功。
- 心跳写入失败记录错误，保留上一份原子状态及其旧时间戳；后台不中断，恢复后再发布。`--once` 在最终心跳失败或包级错误时非零退出。
- 解析子进程启动失败关闭双向管道；移出需求集的包清理进程内时间戳，避免长期服务状态积累。

## 不自动做的事情

不删除用户文件、解析结果或旧证据腾空间；不搬迁WAL数据库到NAS；不自动扩大GPU并发；不提高原文预算；不改变真正坏文件/敏感文件/来源变化的原有处理。已被下层解析器转换为普通警告的异常，本阶段不能反向识别其资源类型。源数据库自身不可读的整轮恢复、全系统磁盘预留协调及解包膨胀预算仍需后续实现。

## 验证

离线测试覆盖阈值/滞回、磁盘检查失败、不同临时卷、初始化失败隔离、同进程延迟恢复、跨进程类型、启动管道回收、原文事务/全文索引回滚、中英泰证据及页码、敏感文件不解析、真正坏文件可见、心跳恢复。额外用独立数据库的 `PRAGMA max_page_count` 触发真实 `SQLITE_FULL`；不是把生产磁盘写满。

## 官方依据

- SQLite Result Codes：FULL也可能发生在单独的临时盘，BUSY/LOCKED与坏文件不同。https://www.sqlite.org/rescode.html
- SQLite Transactions：FULL/NOMEM等可能回滚一个语句或整个事务；显式回滚可保持一致状态。https://www.sqlite.org/lang_transaction.html
- Python 3.12 shutil.disk_usage：查询指定路径所在文件系统容量。https://docs.python.org/3.12/library/shutil.html#shutil.disk_usage

这是资源恢复工程改进，不宣称新增吞吐提升；此前第二阶段的局部速度结论仍以其独立基准为准。
