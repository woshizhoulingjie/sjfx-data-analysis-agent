# SJFX V1–V3 改修结果与交付边界

本文记录本轮改修的交付口径、代码落点和验收状态。它不替代
`PERFORMANCE_ACCEPTANCE.md` 的真实负载结果，也不把尚未在服务器跑过的容量测试写成通过。

## 统一交付口径

- 整个资料包可以是数十至数百 GiB，由大量文件和目录构成。
- 普通单文件、归档容器、归档单成员、单归档累计实际解压内容和一次导出原始内容统一为
  10 GiB 硬上限。
- 100% 清点只表示安全边界内所有普通文件和目录已登记。敏感/不支持内容可以 metadata-only，
  但不能从清单消失；符号链接不跟随并单独计数。
- 内容解析覆盖率和语义分析覆盖率独立于清点覆盖率。大包首轮允许有限语义投影，不能标成
  全文深度分析。
- 扫描安全上限保留且可配置；命中任一文件、目录、节点、单目录条目或深度上限，都必须
  显示清点不完整。

## V1：10 GiB 和大文件底座

| 改修项 | 代码/配置落点 | 结果 |
| --- | --- | --- |
| 中央容量硬上限 | `config.py` 的 `MAX_CONTENT_BYTES`/`content_byte_limit` | 各组件可降低预算，不能超过 10 GiB |
| 普通文件/归档/导出统一 | `config.py`、`.env.example` | 容器、成员、累计解压、源文件和导出示例均为 `10737418240` |
| 专用解析临时根 | `SJFX_PARSE_TEMP_DIR`、`services/unified_parser.py` | 避开容量小的系统 `/tmp`，写入前检查剩余空间和保留预算 |
| 临时资源回收 | 解析父进程和陈旧临时项清理 | 超时、取消、崩溃后回收项目拥有的归档/PDF 修复临时项 |
| 归档安全 | `services/unified_parser.py` | 成员数、路径深度、压缩比、声明/实际大小、累计预算逐项限制；加密成员隔离失败 |
| 扫描安全边界 | `services/scanner.py` | 文件、目录、节点、单目录条目、深度和取消检查均可观察 |
| 导出安全 | `services/exporter.py` | 容量/磁盘预检、流式源哈希、源变化拒绝、`.part` 原子发布 |

## V2：Web 可用性与计算正确性

| 改修项 | 代码/配置落点 | 结果 |
| --- | --- | --- |
| 请求体防护 | `web_compat.py`、`app.py` | 鉴权在读取正文前执行；Content-Length 和 chunked 正文都受真实流式上限保护 |
| Web 不被同步处理阻塞 | `web_compat.py` | 同步兼容视图进入工作线程，请求上下文隔离，并发查询可重叠 |
| 最小扫描授权 | `config.py`、`SCAN_ALLOWED_ROOTS` | 非回环 HOST 必须显式配置白名单；不得默认暴露整个 `/home` |
| 稳定数据归属 | `SJFX_OWNER_ID` | Token 可轮换，历史扫描、任务和导出不再跟着 Token 哈希失联 |
| 大成果下载 | `/api/download-ticket`、`/outputs/<file>` | owner/文件绑定的一次性短期票据；浏览器导航流式落盘，不缓冲 10 GiB Blob |
| 跨文件精确统计 | `services/structured_qa.py` | 同构表跨文件求和、加权平均、全局极值、总行数；异构同名字段拒绝混算 |

## V3：渐进结果与大树分页

| 改修项 | 代码/接口落点 | 结果 |
| --- | --- | --- |
| 首版概览持久化 | `analysis_progress`、Worker 分批进度 | 完整主题分析结束前即可读取阶段、进度、首版概览和当前覆盖 |
| 三类覆盖率 | `services/large_package.py` | `inventory_coverage`、`parse_coverage`、`semantic_analysis_coverage` 分别计算 |
| 有界默认响应 | `/api/scan/<id>`、`/api/analysis/<id>` | 默认返回概览和浅层树；`?full=1` 仅供受控诊断兼容 |
| 树分页 | `tree_nodes`、`/api/tree/<id>` | 物理树/主题树按节点、offset、limit 读取直接子项 |
| 摘要分页 | `/api/summaries/<id>` | 摘要独立分页，不随扫描接口返回全部内容 |
| 前端懒加载 | `static/app.js` | 展开节点或加载更多时才请求下一页，避免一次生成全量 DOM |

## 验收工具

`scripts/benchmark_package.py` 提供两种模式：

- `smoke`：真实执行独立容量测量、清点和分析；检索、恢复、导出为可选钩子。
- `acceptance`：固定要求两次持久化检索、全新 Storage/解析器检查点重入和真实导出，并输出
  `sjfx-performance/2.0` JSON 与退出码。

工具不会改写扫描 size 元数据。它独立遍历所有普通文件/目录，与产品扫描结果核对文件数、
目录数和字节数；在主机可提供分配块信息时拒绝稀疏样本。它还记录进程树 CPU/RSS、磁盘
前后变化、三类覆盖率、检查点复用、导出路径/字节/SHA-256 和每项阈值的 pass/fail。

专属契约测试：

```bash
python -m unittest discover -s tests -p test_benchmark_contract.py -v
```

本地极小真实样本已跑通 `acceptance` 的检索、恢复和导出三个钩子，三个钩子均返回 passed；
容量检查按设计返回 `real_input_size` 失败，没有把极小样本误报为 1 GiB。这个冒烟结果只证明
工具契约有效，不代替服务器真实 1/5/10 GiB 结果。

## 当前仍不能写成“已验收”的事项

1. 服务器真实分配的 1/5/10 GiB 固定混合样本尚需逐档运行并保存 JSON。
2. 数十/数百 GiB 总资料包需要单独验证全包清点、长时间切片续跑和分范围导出。
3. 自动 recovery 钩子验证检查点重入；还需进行一次真实 Worker 停止、失联判定、重启续跑演练。
4. 10 GiB CSV 的全量流式统计不能用当前 256 MiB 有界画像替代，需作为专项能力验收。
5. 移动介质写入后再次校验、独立签名和完整交接链属于后续安全交付加固，不在 V1–V3
   “代码完成”状态中冒充已完成。

正式判定标准与命令见 [PERFORMANCE_ACCEPTANCE.md](PERFORMANCE_ACCEPTANCE.md)。只有真实 JSON
全部 required checks 通过、真实 Worker 恢复演练通过、人工功能核对通过，才可发布
“V1–V3 验收通过”。
