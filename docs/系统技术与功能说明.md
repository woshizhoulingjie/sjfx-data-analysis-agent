# SJFX 数据分析智能体：技术、功能与架构说明

## 1. 系统概述

SJFX 是一个面向未知资料集合的数据分析智能体。它的目标不是直接生成一篇无法核验的长报告，而是帮助用户先回答三个基础问题：

1. 这批资料里面有什么？
2. 哪些内容有价值、值得继续研究？
3. 一个问题究竟由哪些原始正文证据支撑？

系统从服务器上的目录或压缩包开始，经过扫描、解析、画像、去重、聚类、主题组织、证据筛选和深度分析，最终输出可浏览、可追溯、可继续下钻的分析结果，以及可以交给报告整编人员或其他 Agent 的完整交接包。

系统定位可以概括为：

```text
未知数据包
    ↓
内容概览与价值判断
    ↓
主题/子方向下钻
    ↓
问题—回答—证据链
    ↓
定向深挖与整编交接
```

## 2. 设计目标

### 2.1 先概览，再深挖

面对几 GB、几千个文件甚至完全未知的数据包，系统先完成全量目录盘点和有界首轮分析，再由用户选择感兴趣的主题或范围进行补充分析，避免一开始就对所有内容进行高成本模型推理。

### 2.2 结果必须可以追溯

分析结论不能只显示模型生成的文字。每个重要结论都尽量绑定来源文件、页码、章节、表格/行范围、原文片段和内容哈希，用户可以从结论回到原始资料复核。

### 2.3 模型不可用时仍然可用

扫描、格式统计、基础解析、本地检索、去重、覆盖率和导出不应完全依赖大模型。模型超时、输出格式错误或共享 GPU 忙碌时，系统使用本地规则和保底结构返回可用结果，并明确标记降级原因。

### 2.4 数据默认留在本地

系统默认使用本地 Ollama。云端模型能力必须由配置和页面确认共同开启；API、任务、结果和导出均有 Token 鉴权，扫描目录受到白名单限制。

## 3. 总体架构

SJFX 采用“模块化单体 Web + 独立本地 Worker + SQLite WAL”的单机架构：

```text
┌──────────────────────────┐
│ 浏览器前端                │
│ HTML / CSS / JavaScript   │
└────────────┬─────────────┘
             │ HTTP + X-SJFX-Token
             ▼
┌──────────────────────────┐
│ FastAPI / Uvicorn         │
│ app.py                    │
│ 路由、鉴权、任务提交、查询 │
└────────────┬─────────────┘
             │ 写入任务
             ▼
┌──────────────────────────┐
│ SQLite + WAL              │
│ 任务、进度、检查点、结果   │
└────────────┬─────────────┘
             │ Worker 领取任务
             ▼
┌──────────────────────────┐
│ 独立 Worker               │
│ worker.py                 │
│ 扫描、解析、分析、导出     │
└──────┬──────────┬────────┘
       │          │
       ▼          ▼
┌────────────┐ ┌─────────────────┐
│ 本地解析器  │ │ 本地 Ollama/Qwen │
│ Docling    │ │ 主题/摘要增强    │
│ RapidOCR   │ └─────────────────┘
└────────────┘
```

### 3.1 为什么采用 Web 与 Worker 分离

扫描几 GB 数据、解析扫描型 PDF、调用本地模型和生成 ZIP 都可能持续数分钟甚至更久。如果 HTTP 请求直接等待这些工作，容易受到浏览器、反向代理或 Web 服务器超时影响。

因此系统采用：

```text
提交请求 → 立即返回 job_id → Worker 后台执行 → 前端轮询 /api/jobs/{job_id}
```

这样 Web 进程保持响应，任务状态可以持久化，服务重启后还能依据 SQLite 中的任务和检查点恢复。

### 3.2 为什么模型默认串行

系统的文件扫描和部分本地统计可以并行，但共享 GPU 上的 Ollama/Qwen 推理默认使用单并发。原因是多个长上下文请求同时运行时，会同时占用 KV Cache 和显存，容易导致显存不足、系统抖动或影响同一服务器上的其他用户。

串行只限制模型推理，不代表整个系统所有工作都只能串行；扫描、文件清单、轻量解析和导出仍按任务边界执行。若部署到专用 GPU，可通过 `LLM_MAX_CONCURRENCY` 评估提高并发，但必须先做显存和延迟压测。

## 4. 技术栈及其用途

| 技术 | 在系统中的用途 | 解决的问题 |
|---|---|---|
| Python 3.10+ | 后端主语言 | 适合文件处理、数据分析、模型调用和快速迭代 |
| FastAPI | HTTP API 和页面服务 | 提供鉴权、任务提交、状态查询、摘要、检索和导出接口 |
| Uvicorn | ASGI 服务器 | 运行 FastAPI Web 进程 |
| SQLite | 任务、扫描、摘要和索引持久化 | 不依赖 Redis，单机部署简单，服务重启后可恢复 |
| SQLite WAL | 并发读写模式 | 减少 Web 查询与 Worker 写入之间的阻塞 |
| 独立 Worker | 长耗时后台任务 | 避免 HTTP 请求因扫描或模型调用超时 |
| Pydantic / PydanticAI 边界 | 配置、Agent 输入输出和结构化结果约束 | 降低模型漏字段、类型错误和业务 KeyError 风险 |
| Ollama | 本地模型服务 | 在服务器本地执行主题命名、摘要和增强分析 |
| Qwen 本地模型 | 语义理解和结构化生成 | 生成主题、结论、摘要和研究方向 |
| Docling | 高精度文档版面解析 | 提取 PDF/Office 的段落、标题、表格和布局信息 |
| RapidOCR + ONNX Runtime | 图片和扫描件 OCR | 识别扫描型 PDF、图片和 Office 内嵌图片中的文字 |
| pypdf | PDF 轻量正文提取 | 快速模式下低成本读取普通 PDF |
| python-docx | Word 解析与 Word 报告生成 | 读取 DOCX 并生成内容概览 |
| python-pptx | PowerPoint 解析 | 提取 PPT 文本和页面信息 |
| openpyxl | XLSX/XLSM 读取 | 结构化数据画像和表格内容提取 |
| csv/json/jsonl | 结构化数据读取 | 字段类型、缺失值、重复值和统计分布分析 |
| 自研 BM25 | 本地关键词检索 | 在大语料中按问题检索相关正文 |
| scikit-learn TF-IDF | 字符级相似检索 | 处理中文分词不足和词形变化问题 |
| Ollama Embedding（可选） | 语义相似度重排 | 发现没有直接关键词但语义相关的证据 |
| SHA-256 | 内容指纹和精确去重 | 识别不同路径下完全相同的文件 |
| SimHash + LSH | 相似文档聚类 | 发现近似版本、摘要版和内容高度重叠的文档 |
| ZIP/TAR 标准库处理 | 压缩包安全解包 | 支持压缩包输入并限制成员数、大小和解压总量 |
| HTML/CSS/JavaScript | 交互式前端 | 目录树、节点摘要、进度、检索和导出操作 |

## 5. 完整数据处理流程

### 第一步：身份验证和范围校验

用户通过 `X-SJFX-Token` 或 `Authorization: Bearer` 访问 API。系统为 Token 生成不可逆身份指纹，并用它隔离扫描、任务、结果和下载资源。

用户提交服务器目录后，系统将路径解析为绝对路径，检查它是否位于 `SCAN_ALLOWED_ROOTS` 白名单内，拒绝路径越界和未授权目录。

### 第二步：目录扫描

扫描器递归遍历目标目录，记录：

- 文件相对路径和物理目录结构；
- 文件扩展名、大小和修改信息；
- 总文件数、目录数、总大小和格式分布；
- 权限失败、符号链接跳过和目录深度截断信息。

扫描器不跟随符号链接，并受 `MAX_SCAN_DEPTH`、`MAX_SCAN_FILES` 和单文件大小限制保护。

扫描完成后，原始目录树立即返回给前端，后续解析和主题分析继续由 Worker 执行。

### 第三步：统一解析和证据抽取

解析器根据扩展名和文件内容选择路径：

```text
普通文本/PDF
    ├── 快速模式：轻量正文提取
    └── 高精度模式：Docling 版面分析、表格识别、OCR

Office 文件
    ├── 段落、标题、幻灯片、工作表
    ├── 表格与结构化字段
    └── 内嵌图片 OCR

ZIP/TAR
    ├── 安全检查成员路径
    ├── 限制成员数和解压总量
    └── 在受控范围内解析成员
```

每个文件会形成轻量文档投影和证据单元。证据单元尽量携带来源路径、页码、章节、表格/行范围、解析器、内容哈希和正文片段。

### 第四步：结构化数据画像

CSV、TSV、JSON、JSONL、XLSX 和 XLSM 会优先进行本地画像，包括：

- 字段名和字段类型；
- 行数、列数和数据范围；
- 缺失值比例；
- 重复行和重复键；
- 数值字段的最小值、最大值、平均值和分布提示；
- 时间字段的时间范围；
- 异常值和疑似敏感字段；
- 人物、地点、事件等字段提示；
- 数据质量评分和可分析性判断。

画像过程受行数和文件大小限制，并尽量使用流式读取，避免把大表一次性全部加载到内存。

### 第五步：去重与相似聚类

系统先计算 SHA-256：完全相同的内容只保留一个规范文件，其他路径记录为重复来源。

对不完全相同但高度相似的文本，系统使用 SimHash/LSH 形成相似文档组，用于识别摘要版、不同目录副本和版本变体。相似不等于完全相同，导出时会保留明确的关系说明。

### 第六步：主题和自适应目录

系统综合文件正文、标题、结构化画像、分类信号和可选的本地模型命名结果，生成内容主题。展示结构为：

```text
主题
└── 子方向
    └── 文档
        └── 原文证据
```

主题节点保存成员文件、代表文档、摘要、关键结论、证据链和覆盖率。主题节点不是重新创建物理目录，而是对已有分析结果的语义投影。

### 第七步：问题—回答—证据绑定

证据选择由两层质量门槛组成：

1. **证据本身质量**：排除标题、章节名、疑问句、文件名和无事实含义的短主题词；保留可核验正文。
2. **问题相关性**：正文必须与当前问题存在关键概念匹配、可靠间接信号或足够高的语义关联；无关正文不会为了凑数量进入链路。

系统为合格证据抽取最能支撑问题的句子，并注明：

- `直接证据`：正文直接出现问题所需的关键概念并给出事实或解释；
- `间接证据`：正文提供与问题相关的因果、影响或机制信号，需要结合上下文核验；
- `语义证据`：没有直接关键词，但向量语义关联足够强，必须人工复核；
- `证据不足`：当前资料没有足够依据，系统不强行生成确定结论。

### 第八步：定向深度分析

用户选中一个主题、子方向、目录或文档后，可以发起深度摘要或补充分析。后端携带范围路径和主题节点 `node_id`，只加载当前范围对应的文件，避免误用根目录或其他任务的文件。

深度摘要由本地模型生成结构化结果，再经过字段校验、证据 ID 校验和本地降级处理。模型输出不合格时，不会直接将异常字段传到前端。

### 第九步：报告和整编导出

系统可以生成：

- 数据包内容概览 Word；
- 主题/目录节点摘要；
- 多节点组合交接 ZIP；
- 结论—证据链 JSON；
- 解析覆盖率清单；
- 原始资料索引、去重清单和聚类清单；
- 本地检索结果和整编任务说明。

导出前用户必须填写明确的整编任务主题。导出按照文件内容 SHA-256 自动去重，并记录多个选择最终映射到的规范源文件。

## 6. 功能说明

### 6.1 数据包概览

展示文件构成、目录数量、格式分布、数据质量、价值判断、主题概览、主要发现、推荐问题和未分析范围，帮助用户先判断“这批资料值不值得继续投入时间”。

### 6.2 原始目录树

完整保留服务器物理目录结构，用于核对输入范围、发现遗漏文件、确认文件来源并定位解析失败项。

### 6.3 语义主题树

按照内容而非路径组织资料，支持主题、子方向、文档、证据四级下钻。每个节点都有成员文件和覆盖信息。

### 6.4 节点摘要与深度摘要

普通节点摘要使用本地规则和已有解析结果快速返回；深度摘要通过 Worker 调用模型，对选定范围进行更完整的归纳、价值判断、研究问题和证据绑定。

### 6.5 本地 RAG 证据检索

在整个数据包或当前节点范围内输入问题，使用 BM25、TF-IDF 和可选 embedding 进行混合排序，返回可定位的正文证据。该功能默认不需要云端模型。

### 6.6 精确数字问答

只用于结构化数据画像后的确定统计，例如合计、平均、最大、最小和记录数。它不是通用聊天，不会在找不到字段时编造数字。

### 6.7 补充分析和失败重试

大包首轮分析后，用户可以只对关注主题或目录继续分析；解析失败的文件可以单独重试，已经完成的文件通过缓存和检查点复用。

### 6.8 多节点组合导出

支持同时选择多个主题、目录、文档或证据。系统自动合并重叠范围、去除重复源文件并生成统一交接说明。

## 7. 大数据包能力和边界

当总大小达到 1 GB 或文件数达到 3000 时，系统进入大数据包模式：

```text
全量扫描清单
    ↓
有界首轮解析
    ↓
显示已分析/待分析/失败覆盖率
    ↓
按关注范围分批补充
    ↓
选择性深度摘要与导出
```

系统面向 4–5 GB 数据包设计了分层处理、压缩侧存、批次限制和检查点，但实际速度取决于文件数量、扫描件比例、OCR 和磁盘 IO。4–5 GB 不应理解为一次把全部正文装入内存或一次性发送给模型。

关键边界包括：

- 最大扫描文件数和目录深度；
- 单文件大小、解析时间和 Worker 内存；
- 压缩包成员数、单成员大小和总解压大小；
- 首轮解析文件数和补充分析批次大小；
- 结构化数据最大行数和画像字节数；
- 导出 ZIP 最大字节数。

所有边界都会在概览或状态接口中体现为覆盖率、待处理数量、失败数量和警告，不把部分分析伪装成全量完成。

## 8. 安全与可靠性设计

### 8.1 访问控制

所有 API 和成果下载支持 Token 鉴权。任务、扫描和结果绑定 Token 指纹，避免不同用户互相读取数据。

### 8.2 路径安全

扫描目录必须命中白名单，系统拒绝路径越界、符号链接循环和超深目录。

### 8.3 资源安全

单文件大小、解析超时、内存、文件总数和压缩包解压量都有上限，防止异常文件拖垮 Worker。

### 8.4 任务恢复

任务状态、心跳、失败原因、取消标记和检查点保存在 SQLite。Worker 发现过期任务后可以恢复或重新排队，前端通过轮询获得状态。

### 8.5 存储安全

SQLite 使用 WAL 和事务；大正文采用压缩侧存；导出先写临时文件再原子替换，避免并发写入产生半个 ZIP 或损坏结果。

### 8.6 模型输出安全

模型返回内容先经过 JSON 提取、字段校验、证据 ID 校验和默认结构降级。日志只记录任务 ID、阶段、耗时和错误类型，不应记录完整 Token、提示词或用户正文。

## 9. 典型使用场景

### 场景一：拿到未知研究资料包

用户导入目录后先看数据概览和主题树，判断资料主要涉及哪些方向；再选择一个方向进行深度摘要，查看关键结论和原文依据。

### 场景二：分析混合格式项目资料

系统同时解析 PDF、Word、PPT、Excel 和图片，统一形成文档索引。用户可以按主题查看跨格式资料，而不必逐个打开文件。

### 场景三：核查数据问题

对 CSV/XLSX 做质量画像后，用户可以查看缺失值、重复值、异常值和时间范围，并通过精确数字问答核对关键统计。

### 场景四：向报告整编 Agent 交接

用户勾选多个主题和关键证据，输入整编任务主题，导出已去重的原始资料、结论—证据链、覆盖率和交接说明，交给下一阶段的报告整编流程。

## 10. 当前限制和人工责任

- 低清扫描件、加密文件、损坏文件和复杂嵌套表格可能无法完整解析；
- 大数据包首轮是概览和抽样，不等于逐字阅读全部文件；
- 自动主题、价值判断和语义证据应由人工复核；
- 精确数字问答依赖字段类型和单位识别，关键数字仍应回查原表；
- 系统负责资料理解和证据化交接，不替代最终报告作者对事实、版权、保密和引用的责任。

## 11. 一句话总结

SJFX 是一个以本地处理为主、以覆盖率透明为边界、以问题—回答—证据链为核心的数据分析智能体：它先帮用户看懂一批未知资料，再让用户围绕有价值的问题逐步下钻，最后把可复核的原始材料和分析成果交给后续整编流程。
