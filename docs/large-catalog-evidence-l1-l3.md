# 大数据包智能目录 · 取文改造 L1–L3 规格与进度

> 本文件是这次改造的**唯一权威规格**。每轮开工先读它，收工更新"状态"列。
> 目标：100GB（约 21 万文件，均值 500KB）在 **10 小时**内产出**高质量**智能目录。

## 0. 成本模型（实测，决定了所有取舍）

| 项目 | 实测 | 含义 |
|---|---|---|
| 输入 token（证据） | **0.7 ms/token**；命中前缀缓存后 ≈ 0 | 让模型"多看"很便宜 |
| 输出 token（模型写字） | **22 ms/token**（43–46 tok/s） | 让模型"多说"才贵，贵 30 倍 |
| 每次命名调用 | 3 组 ≈ 13.7 s（≈6,000 token） | 时间 ≈ 总 token × 2.3ms |

**结论：证据（输入）可以大方加，输出必须锁死。**

## L1 · 文件层（每份文件的取文与质量）

| 编号 | 内容 | 状态 |
|---|---|---|
| L1.1 | **结构化档案进命名 payload**：每份证据带 `fields`(≤5)、`keywords`(≤6)、`headings`(≤3)，并给出组成员数 `members` 与抽样数 `sampled`；预算裁剪顺序为 正文→关键词→字段→丢证据 | ✅ 已完成 |
| L1.2 | **跨文件模板检测**：统计同批文件的行级/短语级文档频次（DF），把出现在 >30% 文件里的短行判为页眉页脚/封面模板，汇成**包级模板词典**，从证据与 L2 画像中剔除 | ✅ 已完成（真实数据验证见下） |
| L1.3 | **统一质量闸门**：`is_garbled()` 接入 k-means 启用路径（此前只挂在旧 greedy 路径）；HTML/XML 源码在 `material()` 里剥离，剥不干净则走既有"无正文"路径；被判不可用的文件不拿向量、不参与语义归纳，但保留在清单与画像里（`portrait.catalog_quality`），并从 `material_pending_count()` 排除（否则聚类永不触发） | ✅ 已完成 |
| L1.4 | **组几何**：`split_off_outliers()` 在成员搬移的同一事务里重算父子两组 `anchor`/`representative`；历史空质心组用 repair `R10` 回填（**dry-run 已确认 193 组**） | ✅ 代码完成 / R10 待批准执行 |

## L2 · 组层（组画像，替代"随机 5 份裸片段"）

| 编号 | 内容 | 状态 |
|---|---|---|
| L2.1 | **组画像**：基于该组**全部成员**的档案（不是成员向量）做 **c-TF-IDF**，字符 n-gram(2–4)（生产未装 jieba，`retrieval.py:164` 已有 char n-gram 先例），按**文档频次**加权，剔除 L1.2 的模板词典 | ✅ 已完成 |
| L2.2 | 画像输出三块：**区分性短语 Top-N（带支撑文档数）** / **共同研究对象与核心问题** / **少数派子题** | ✅ 已完成 |
| L2.3 | 缓存键 = 组 ID + 成员修订号 + 抽样策略版本 + 分词器版本；CPU 几秒/组，**0 模型 token** | ✅ 已完成（实测 0.09–0.65s/组） |
| L2.4 | 画像作为 payload **第一块**（固定格式，对前缀缓存友好；命中时预填充≈0） | ✅ 已完成 |

## L3 · 样本层（选得准，而不是选得"最不同"）

| 编号 | 内容 | 状态 |
|---|---|---|
| L3.1 | `selection_score(d) = λ·relevance(d) − (1−λ)·max_sim(已选)`，λ 初值 **0.7**（相关性为主），复用已存向量，毫秒级 | ✅ 已完成 |

### A/B 暴露并已修复的画像污染（共 8 项）

A/B 里发现论文组的画像被 `Cent / 1313 / CC-BY-NC-ND / edia / died` 这类碎片占满。逐层排查后修掉 8 个问题——**其中 4 个是后续复盘时发现的、我自己引入的缺陷**：

| # | 问题 | 修法 |
|---|---|---|
| 1 | 对英文取 2–4 字符 n-gram 只能产出碎片 | **按字符集分开取词**：CJK 用 2–4 字窗口，拉丁文取整词/词组 |
| 2 | 英文功能词（that/here/with）每篇都有，被 DF 当成共同主题 | 英文功能词表 |
| 3 | 页眉页脚"本组高频但整包背景不高频"，背景规则抓不到 | **位置判据**：≥70% 文档首尾固定位置出现 → 判为版式 |
| 4 | 中文任意两字相邻都成词（`于国`、`则第`） | 二字词支撑门槛提到 df ≥ 3 |
| 5 | **合并只在 2–4 字符窗口找种子** → `learning`/`memory` 这类 7–8 字母的词**永远进不了画像**（这解释了为什么论文组只剩 `role/care/data` 这种 ≤4 字母的词） | 合并改为"种子的所有出现位置求并集"，与长度无关 |
| 6 | `phrase_stats` 同样只查 2–4 字符子串 → 整词/词组型短语**算不出分数被整条丢掉** | 改为遍历**组成该短语的种子** |
| 7 | 拉丁词表是**过滤后**的，相邻性丢失（`state of the art model` → 假短语 `state model`） | 按**原文位置**判断相邻 |
| 8 | 词组跨空白，而合并按空白切段 → 词组全被段边界挡住 | 合并加一趟"只用含空格的种子在整篇上扫"的通道 |

**还有一条统计规则本身解决不了的**：出版商许可声明（`perpetuity / granted / licenseavailab / authorscontrib / preprintthis`）只出现在约 40% 文件里、位置不固定，而且**确实在本组更常见**（该组是同源论文）——统计上区分不了"同源样板"与"本组主题"。只能靠**学术/出版类样板词表**清掉（长词还做子串匹配，因为 PDF 抽取会把词粘成 `licenseavailab`）。

**待标定项（已解决）**：异质性阈值原本是绝对值（0.95/0.90）。专家报告提醒"从某份语料统计出来的阈值换一份语料会失效"，实测也印证——cssj1 这类网页/汇编语料的组内余弦本来就高（0.968–0.984），论文包 0.931 已算异质。现改为**相对同包基线**：`package_baseline_coherence()` 采样最多 300 个成员的向量到**包质心**的平均余弦作为参照，判据变成"本组内聚度 − 包内典型内聚度"（≥+0.05 少给样本、≥0 居中、<0 多给）；拿不到基线时才退回绝对阈值。

**子区域覆盖改为按结构判定（重要修正）**：原先覆盖份数写成 `want//3`，样本数一变小（包内基线判为同质组 → 6 份）配额就退化成 2，三个子区域必漏一个——契约测试 `test_representatives_cover_distinct_content_with_same_budget` 正是这样挂的。现在改成"**只要还存在与已选都明显不同（gap ≥ 0.10）的文件，就再开一个子区域**"：同质组自然早停，异质组自然覆盖全。

`km-6e46623a-00001`（101 成员，当前名「数据库与数据工程领域文献汇编及核心概念整理」）画像：
- **distinctive**：联合国人权事务委员会(13)、国家机关事务管理(13)、书目索引、图书馆项目、搜索引擎
→ 画像**直接暴露该组并不是"数据库与数据工程"**，而是一堆百科条目混在一起（应当判为 mixed）。

实现要点（都是真实数据上踩出来的）：
1. 模板短语末尾空格导致精确匹配全部落空 → `strip_templates` 改为**忽略空白差异**的正则匹配。
2. `keywords` 本身常常就是页眉 → 新增 `filter_meta`，字段也要过模板过滤。
3. "本组高频"既可能是模板也可能是主题 → `meta_templates` 用**本组高频 ∧ 整包背景也高频**判定（背景样本 <20 份时不判，保守保留）。
4. 整包范围都在用的短语（≥50% 背景文件）直接排除，且合并结果要**复查**（否则 `工程技术`+`术中心` 又能拼回 `工程技术中心`）。
5. 短语区分度取子串 **IDF 最小值**（最不具区分度的成分决定），取最大值会把整包套话抬回来。
6. 语料是"条目/表格行"用空格拼起来的 → 画像**只在段内**取短语（否则造出 ` 表 项目 数量 备注 ` 这种假短语、把相邻条目粘成 `容器 共識`）；模板检测仍跨段。
7. 一个真 bug：`len(set(text)) <= 2` 当"重复字符"判据会把**所有二字词**砍掉。

### 第 1 项实现记录

**问题（实测）**：两条命名路径各写一套失败处理——单组 `process_one` 会识别"依赖不可用"、长退避（120s）、**不递增 attempts**、并退回轮次额度；批量 `process_batch` 统一走 5 秒短退避 + attempts+1 且不退款。一次模型宕机（生产注释记录过 2h20m）在批量路径上会把成百上千个任务的退避额度烧掉。台账最近 200 次批量调用 **21 次 failed**，而组内失败还被整次记成 `completed`。

**改动**：
- `naming.classify_failure()`：统一五个类别 —— `unavailable` / `invalid_output` / `stale` / `cancelled` / `budget`（外加 `unknown`、以及"只是释放本次领取"的 `released`）。
- `naming.release_job()`：**两条路径共用**的释放收口。类别决定状态与退避：不可用=不递增 attempts + 长退避；非法输出=指数退避 + 递增；陈旧=立刻回 queued；释放=立即归队不改计数。UPDATE 带 `AND status='running'` 保护，**不会覆盖已发布或已释放的状态**。
- 批量路径删除自己的 `_release`，改走同一收口；并在不可用时与单组路径一样 `refund_call()` 退回轮次额度。
- `lp_catalog_calls` 新增 `detail` 列（**增量加列**，本表所有写入方都用显式列名，旧代码可继续读）：记录 `published` / `failed[{group,category}]` / `reserved_groups`，以及 `usage_state`（`measured` / `estimated`——缺 usage 时按预留保守结算并如实标注，**不把缺 usage 当零成本**）。
- 调用状态如实反映组级结果：全部发布=`completed`、部分=`partial`、都没发出=`failed`、被暂停打断=`stale`。

**测试**：`test_catalog_evidence_quality.py` 新增 `FailureHandlingTests`（分类覆盖、不可用不烧 attempts、非法输出递增、纯释放不改计数、**不覆盖已完成任务**）；`test_catalog_batch.py` 新增两条批量契约测试（**partial + 逐组结果**、**宕机时与单组路径同款处理：refunded + requests 归零 + attempts 归零**）。

### 第 2 项实现记录：三条"零调用"路线实测均不可用

原计划是"零调用的支撑检查"。**在真实数据上做了三次判决性对照实验（真名 vs 从别的包随机取的名），三次都不可用**：

| 方案 | 真名 p10 / p50 | 假名 p90 | 可分性 | 最佳阈值下的代价 |
|---|---|---|---|---|
| 嵌入名称 vs 组质心（多语言 e5，跨语言可行） | 0.824 / 0.887 | 0.894 | **−0.071（完全重叠）** | 准确率 71%，**42% 真名被误判** |
| 名称三元组 vs 正文证据 | 0.000 / 0.143 | 0.105 | **−0.105（重叠）** | 准确率 75%，**50% 真名被误判** |
| 名称二字组 vs 结构化档案词表（标题/关键词/字段/画像短语） | 0.000 / 0.000 | 0.050 | **−0.050（重叠）** | 准确率 69%，**53% 真名被误判** |

原因：模型本来就在**改写与概括**（这正是专家警告的 "do not replace semantic validation with a brittle exact-word rule"），而这类语料任意两篇的余弦基线就有 0.84、判别区间只有 0.1。留出成员也没有额外判别力——`cos(名,全组)` 与 `cos(名,留出成员)` 几乎完全同步（p5 0.832 vs 0.821，中位 0.887 vs 0.892）。

**因此改了做法**：
1. 实现**可靠且便宜的那部分** —— 长清单式名称守卫（§4.6）：名称含 ≥3 个顿号说明它在罗列而不是概括，置 needs_review 但保留名称（硬拒会白费一次重试）。一到两个顿号是正常层次表达，不触发。
2. 提供**唯一可行方案的工具**：`scripts/catalog_name_support_audit.py` —— 把**没参与起草名称的成员**（排除被引用证据、按路径散列稳定抽样、优先较长片段）交给模型，只问一句"这些材料与这个名称是不是同一个主题"。实测 **1.15s/组**。

**抽样审计结果（18 组，两轮口径）**：首轮问"是否支持"得 61%，但理由是"材料仅含遗址博物馆，缺姓氏、天文等内容"这类——**审计本身过严**；改成"是不是同一个主题、允许只覆盖一部分"后得 **39%（7/18）不一致，且这 7 组全部 `needs_review=0`**（系统自己没标出来）。

**更重要的解释**：把那 7 条的理由逐条看，绝大多数不是"名字凭空编造"，而是"**组本身是混合的，名称只覆盖了其中几个子题**"（"材料仅含村镇，无河流及铁路站点"、"含婚礼场地等无关内容"、"含瑞典历史及人物传记，非地理气象主题"）。也就是说，**残余质量问题的主因仍是分组边界，不是命名编造**——这与第 3、4 项的判断一致。

### 第 2 项补齐（本轮）：`bundle` 提供留出成员 + `validate` 软支撑评分

报告 §4.3–4.6 要求的原话是"证据包里要额外给一份**没有参与起草名称**的成员片段做对照"，否则"名称与证据一致"是循环论证。已实现：

- `naming.held_out_members()`：按路径散列确定性取 4 份**未参与命名**的成员（组成员 ∩ 非被引用证据），各截 200 字。**它不进 payload、不进 digest**——送进模型的输入一个字都没变，模型结果缓存继续有效。跨留出材料重复的 12 字串当模板剔除，但**剔完剩不下 20 字就退回原文**（第一版把 12 个成员的组剔成"没有留出成员"，这种"过度剔除"本身就是个坑）。
- `naming._name_units()` / `name_support()` / `support_score()`：名称切汉字 3 元组（去掉含 ≥2 个停用字的），分别对**被引用证据**、**留出成员**、**L2 画像的区分性/共同短语**算字面支持度。
- `validate()` 只在三条**同时**成立时置 `needs_review`：`cited ≥ 0.5`（名称确实在照抄模型读过的那几份）、`held_out < cited/2`（组里其余成员几乎不支持）、`profile == 0.0`（名称单元完全不在**非空**的全组画像里）。画像为空时**不判断**——没有画像不等于名称没有支撑，拿"缺席"当证据正是要避免的错误。**绝不改写名称、绝不硬拒**。
- 留出成员**不能**用来放宽既有的编号/术语核对（那条只认被引用证据），否则加一份对照材料等于把防编造守卫拆掉了——有专门的测试钉住这一点。

**真实数据命中率（150 组抽样）**：`cited` n=137（p50 0.0 / p90 0.409）、`held_out` n=90（p50 0.0 / p90 0.3），**只标出 1 组**。它基本不打扰复核者，同时也印证上面的实测——判别力确实很低；定位是"排序人工注意力"，不是判据。

**生产库副本上的端到端取证**（用 sqlite backup 在线复制 1.67GB，用完即删，全程不写生产库）：6 个 162–197 个成员的真实组，每组都拿到 **4 份留出成员、无一与被引用证据**的路径重叠**；`validate()` 在真实组上正确算出三种 score（英文组没有汉字可核对 → `support=null`，明确"不判断"，不回落到假分数）。部分组的留出成员前缀与 payload 里某条证据的**开头 16 字相同**——逐条查证过：那是这个包**每份文件都带同一段汇编页眉**造成的巧合（payload 里那段的来源是它自己引用的证据，不是留出成员），不是泄漏。

`topics._material()` 的 scope 改动见第 5 项；本项新增测试 7 条（`HeldOutSupportTests`）。

### 第 3 项实现记录：不做"搬动前核对"，改成"不给它们起名"

原做法是：模型在命名时指出"某些成员明显不属于本组"，就把这些少数异类摘出去**单独成一个新叶组并再命名一次**。问题在于"这撮人自成一类"这件事在本语料上**无法验证**。为这句话做了四次判决性对照实验，四次都不可用：

| 实验 | 真 split / 正对照 | 同包随机子集 / 负对照 | 结论 |
|---|---|---|---|
| 子组内聚度（余弦均值） | p10 = 0.920 | p90 = 0.966 | **完全重叠**；阈值 0.92 只挡住 18% 随机子集；内聚度主要由**规模**决定（2 人组 p50 0.961 vs 5–9 人组 0.934） |
| 置换检验（对同父组同规模随机子集的零分布，p≤0.05） | **0/13 通过 = 0%** | 5/72 = 7% | **功效为零**：连"取最远两点二分"这种组内最大差异的切分都判不出来；判别力方向甚至是反的 |
| 名称向量 vs 组质心 | 真名 p50 = 0.887 | 假名 p90 = 0.894 | 最佳阈值准确率 71%，**42% 真名被误判** |
| 名称词面 vs 证据/档案词表 | 真名 p50 = 0.143 / 0.000 | 误判率 | **50% / 53% 真名被误判** |

根因还是那句：任意两篇的余弦基线 0.84，而 2–12 份**任意**子集的内聚度都在 0.94 上下。

**因此改了做法（默认行为）**：摘出来的异类**不再新建命名叶组**，而是移进本包既有的系统桶 `km-other-<sha8>`（命名、主题层、合并流程都已排除它；显示名为确定性的"未能识别内容"）。道理是：没有验证手段时，**编一个名字比不给名字更糟**——它把"不知道"包装成一个看起来确定的主题，用户无从分辨。具体实现：

- 桶的建法与 `semantic.py` 完全一致（`status='named'`，空质心，桶本身不进命名队列），文件仍在清单与成员表里，向量不变，下次重聚类可以重新安置。
- 桶的 `result` 里**有界**记录每次摘除的原因（`holds` 只留最近 20 条：父组、父组成员数、搬走几个、时间），不随拆分次数无限增长。
- 每次拆分**被接受或被拒绝**都记原因（`no-outliers` / `outliers-not-in-evidence` / `group-gone` / `singleton` / `outliers-not-members` / `stale-or-locked` / `budget-exhausted(n/max)` / `take==members`），专家报告 §3 要求的"保留预算同时保留判定依据"两条都落地。
- 父组几何照旧在事务内按**搬走之后**的成员重算（空质心会让代表性选择退化成按路径序任取）；桶**保持空质心**——它的语义就是"还没有主题"，给它算质心反而会让它出现在相邻组搜索里。
- 开关 `SJFX_LP_LEAF_SPLIT_NAMED`（默认 0）保留旧行为做 A/B 与回滚；`SJFX_LP_LEAF_SPLIT` / `_MAX` 预算不变。
- **附带收益**：每次摘除不再多花一次命名调用（原来 +1 组 +1 调用），100GB 预算里这部分的调用数下降。

**测试**：`test_catalog_evidence_quality.py` 新增 `LeafSplitPolicyTests`——默认落桶（不新建命名组、不排任务、桶空质心、父组几何重算、预算照记、原因入库、**核对结果入库**）、开关置 1 恢复旧行为、连摘 25 次后 `holds` 有界、每次拒绝都留下 reason。

**本轮补齐：搬动前的成员向量核对（§3.2 原文要求的那一步）。** `naming._subgroup_geometry()` 在被摘出的子组上算三件事并写进 `holds[-1]['check']` 与日志：子组**自身内聚度**、子组质心与**父组质心**的相似度、以及两者之差 `spread`（越大越像"自成一体"）。**它算出来、记下来，但不据它放行或拦截**——因为它的判别力已被四次实验证明为零，据它决策只会把"不知道"换成另一个看起来确定的错误答案。留着它的意义是：以后要重新评估这条判据时，库里有真实分布可查，而不是只有我们的一句话。日志形如：

```
leaf split package=… group=… mode=holding n=52 -> parent=50 moved=2
           check={'members': 2, 'cohesion': 0.99, 'parent_cos': 0.97, 'spread': 0.02} (used=31/240)
```


### 第 4 项实现记录：`scripts/catalog_boundary_audit.py`（零模型调用、只读、3.5s 跑完全库）

第 2 项的审计指向"残余质量问题主因是分组边界"，所以这一步做**检测与暴露**，**不做自动修复**（修分组只能靠模型猜，而搬动前核对的判据已被证明为零功效——自动重分组只会把"不知道"变成另一个看起来确定的错误答案）。

三条判据，都不含"从某份语料统计出来的常量"：

1. **`misplaced-members`（唯一无阈值判据）**：某个成员离**别的**组的质心比离自己组的还近。它不需要任何阈值就能说明"按最近质心它不该在这里"。注意 k-means 若用同一批质心做分配，这条恒为空——**一旦非空，就说明质心在分配之后被改过**（叶子拆分重算几何、R10 回填、增量嵌入、新文件并入），那些组的边界已经陈旧。
2. **`twin-centroid`**：两个组互为最近邻且相似度位于本包最高一档 → 一个主题被切成两个组。报告里同时给出**本包最近邻相似度中位数**做对照（例如某对 0.9200 出现在 p50 = 0.9716 的包里，其实并不异常），并要求两侧各 ≥3 个成员——一两份文件的组对合并了也没有目录价值。
3. **`low-coherence` / `outlier-heavy`**：组内平均内聚度、以及"离质心最远那一撮成员"的位置。这条**是包内相对排名**，按构造总会挑出固定比例的组，只用于排序、不是判定。

**本轮补上另外两条判据**（对应 §5 要求的"最近/次近间隔"与"区分性短语冲突"）：

4. **`single-neighbour`（最近/次近间隔）**：最近邻减次近邻的差距位于本包最高一档、**且**最近邻本身高于本包中位。含义是"这一组只有**一个**像样的邻居"——那一个就是被切开的同一主题。全库只命中 **3 个组**（条件很紧：既要间隔大，又不能是"一个弱邻居"），命中即是强线索。反过来，间隔小说明它处在一片密集邻域里，合并解决不了问题。
5. **`phrase-conflict`（区分性短语冲突，只读名称、零调用）**：同一个包里恰好有 2–3 个组的**名称**共享一个少见的 4–8 字汉字短语（状态名与含泛化词的名字先排除）。名字撞一个少见短语，几乎是"同一个主题被切成两个条目"的直接证据。全库命中 **950 个组**，是本次新增判据里覆盖面最大的一条。

**首次全量结果（生产库，只读，3.5–15s，随并发写压力浮动）**：可疑组 **1,468** 个（五条判据合计）；其中 `misplaced-members` 命中 **626 个组、涉及 5,746 个成员**，这些成员的"离得更近"程度分布是 `<0.005` 边际 2,295 个 / `0.005–0.02` 明显 2,233 个 / **`≥0.02` 显著 1,218 个**；`twin-centroid` 63 个组、收敛出 4 对规模 ≥3 的疑似重复组对；`phrase-conflict` 950 个组；`single-neighbour` 3 个组。最有代表性的一个：`km-d5a73e75-00562`（126 个成员，"法律法规与司法案例汇编资料"）有 **88/126** 个成员更靠近别的组质心（平均 +0.046）。另外还发现 **63 个组的名称就是十六进制 id**（旧命名路径遗留），一并报出来。

**分数最高的那些组几乎都同时命中 3–4 条判据**，例如 `a9d8d9512b6a78c190f0be90`（10 个成员）：5/10 个成员错位（最大 +0.052）+ 与另一组互为孪生（0.9395）+ 内聚度包内 p1 + p10 包内 p1 + 名称撞少见短语。**多判据交叉命中是这份清单最值得先看的部分**——单条判据都可以用"语料本来就这样"解释掉，四五条一起命中就很难是巧合。

**每包整体几何（本轮补上，作为验收指标"组内一致 / 相邻标签区分"的来源，按组数加权）**：组内内聚度中位 **0.9830**；最近邻相似度中位 **0.9451**、**p90 = 0.9975**。最后这个数字是本项最有力的证据：**有十分之一的组，最像它的那个邻居与它几乎重合**——两个几乎一样的组并列在目录里，名字再准也没用。

**本项还修掉两处自身缺陷（都会伪造证据）**：① 单组包（或最近邻算成自己）时 `best = -inf`、`mutual` 恒真，会伪造出"与自己做孪生"，实测报了 3 条假阳性；② 各包清单首尾相接导致"第一个包里的弱证据"排在"最后一个包里的强证据"前面（报告前 15 名里混进 0.001 分的记录，而库里有 5.5 分的组），现在全局重排，并让排序分数**同时**看错位比例与幅度（否则"20 个成员里 1 个偏离 0.0001"会和"3 个里 1 个偏离 0.05"同分）。

**这个数字是本次改造最重要的发现之一**：1,218 个成员按最近质心就"放错了组"，与第 2 项审计的"39% 组被判与留出成员不同主题、理由绝大多数是混合组"完全一致。**分组边界的陈旧/混杂，是残余质量问题的主因**，而不是命名质量。

### 第 5 项实现记录：父主题层每个子节点都带 scope

`topics._material()` 原来只给前 **2** 个采样子节点带 `scope`（`if i < 2`），理由是省 token。但实测输入只值 **0.7 ms/token**（命中前缀缓存时 ≈0），输出是它的 **30 倍**；而主题层每批最多采 `_sample(..., limit=12)` 个子节点，全带上范围最多多花约 **300 token**。代价可以忽略，换来的是提示词里"须综合全部证据"这句话对 12 个子节点都成立（原来 10 个只有名字，主题层看不到它们各自的范围，只能猜共同点）。

### 第 6 项实现记录：`scripts/catalog_acceptance_sample.py`（只读库 + 零模型调用）

分层抽样（包 × 组规模桶 × 有无当前标签）生成人工盲评卡（Markdown）+ 自动指标（JSON），零模型调用、只读库、42.5s 出 150 张卡（0.29s/组）。

**抽样设计上的三个取舍**（都能用参数改回去）：
1. 抽样框默认是**全部组**而不是只叶组：本库有名组里多数已被主题层覆盖（3035 个有名组中只剩 1003 个是叶子，其中 986 个在同一个包），只抽叶组会让评审集退化成单包样本，而"叶不叶"还随主题层重建而变（两次运行之间 5,137→5,151），拿它当抽样框会牺牲可复现性。

### 11. 两条文件车道：实测调参与定稿（2026-09-20）

**硬件实况（决定了所有取舍）**：Xeon E5-2620 v4，**8 物理核 / 16 线程**（cpu0-7 是 8 个不同物理核，兄弟是 0-8/1-9/…）；内存 31GB；**1× RTX 3090 24GB**，被 27B-int4 占 22.9GB（94%），显存只剩约 1.6GB；机器**有别的用户**（`/home/mumu/sci-fuzz` 常驻）。

**预览车道**（同一批 240 个真实文件，子进程沿用生产的 `nice(5)` + 单线程）：

| 并发 | 文件/秒 | 单文件中位 | 平均并发度 |
|---|---|---|---|
| 2（原默认） | 7.52 | 0.226s | 1.97 |
| 4 | 14.81 | 0.221s | 3.92 |
| **8（定稿）** | **21.68** | 0.263s | 7.67 |

2→8 是 **2.9×**，单文件延迟基本不变——这条车道是 I/O 等待型，加并发几乎线性获益。**定稿 `SJFX_LP_PREVIEW_CONCURRENCY=8`**（写进 `bin/sjfx_restart.sh` 的 large_package_worker 启动行）。

**嵌入车道**（同一批 256 条**流水线真正嵌入的文本**，字符长度 p50 746 / p90 1579）：

| 配置 | 文件/秒 | 核秒/文件 | 有效并行度 |
|---|---|---|---|
| OMP=4 准入=2 + 客户端**串行**（改造前） | 6.94 | 0.906 | 6.9 |
| **OMP=4 准入=2 + 客户端并发 2（定稿）** | **7.73** | 0.906 | **7.00** |
| OMP=8 准入=2 | 7.47 | 1.514 | 11.30 |

三条实测结论：
1. **瓶颈是 CPU 核**：4 线程 × 准入 2 已用满 8 个物理核（有效并行 7.00/8）；线程提到 8 只快 **7%** 却多烧 **1.7×** CPU（有效并行 11.3 = 互相抢核）。在有别人的机器上不划算，**定稿保留 OMP=4 准入=2，并给 unit 加 `Nice=5`**，我们的批处理永远让位于别人的负载。
2. **客户端并发是必需的**（1.9× 长文本 / 1.11× 真实短文本）：客户端内部 `BoundedSemaphore(1)` 使"同一实例多线程发块"根本不会并发（第一版实测撞互斥后抛"忙碌"），所以每块要用**独立客户端实例**。它现在把服务压到 7 核满负荷，是前置条件而非主要收益。
3. **冷启动是真的**：服务空闲后第一个请求实测 **21.46 秒**（随后同样内容 0.09s），而共享客户端超时 8s —— 服务一重启第一批嵌入必然失败。本车道单独用 `SJFX_LP_EMBED_TIMEOUT=60`。

**定稿参数**（写进运维脚本，有备份、可回滚）：

```
SJFX_LP_PREVIEW_CONCURRENCY=8     # 预览并发 2→8（实测 2.9×）
VLLM_EMBED_MAX_BATCH_SIZE=16      # 单请求批 8→16（长文本样本实测 1.64×）
SJFX_LP_EMBED_CONCURRENCY=2       # 2 个独立客户端实例 = 服务端准入上限，不超发
SJFX_LP_EMBED_TIMEOUT=60          # 覆盖实测 21s 冷启动
```

**折算 21 万文件（实测单位成本 × 规模）**：

| 车道 | 单位成本 | 21 万文件 | 说明 |
|---|---|---|---|
| 预览 | 0.26 核秒/文件（本样本） | 15 核小时 | 生产历史样本更轻（13–16 文件/秒 @ 并发 2）→ 实际 8–15 核小时 |
| 嵌入 | **0.906 核秒/文件** | **53 核小时** | 硬瓶颈 |

| 命名（GPU，与上面重叠） | ≈4.6 秒/组 | 120–400 组/包 | 单卡 3090 带宽饱和，加并发不增吞吐 |

⇒ **10 小时目标可行，但余量只有 1–2 小时**。**嵌入车道已经无法再用参数提速**——要真正宽裕只有两条路：加 CPU 核，或**把嵌入搬到 GPU**（3090 空闲显存约 1.6GB，e5-small fp16 约 0.25–0.5GB，**可能装得下**；这是不加硬件的唯一宽敞路径，需先验证显存余量）。

### 12. 提速会不会影响质量？逐条实测（2026-09-20）

用户问"现在的改动会影响质量吗"，逐条实测而不是推理：

| 检查 | 实测结果 | 结论 |
|---|---|---|
向量数值：批 8 vs 批 16 vs 并发路径 | 元素最大差 **4.5e-8**、余弦最小 **0.99999994**、**0/64 超过 1e-6** | 不可能翻转分组（分组用的余弦余量远大于此） |
同一配置重跑的噪声底线 | 元素最大差 **0.000e+00**（逐位一致） | 差异确实来自批大小，不是随机性 |
分组算法 / 抽文规则 / 命名提示词与证据选择 | **一行未改** | 速度车道只改"何时算完" |
向量缓存 | 按内容摘要缓存，已算过的不重算 | 并发不会让既有文件换向量 |

**但发现一处真实的不确定性，而且不是本次改造引入的**：预览有 **4 秒时间预算**
（`SJFX_LP_PREVIEW_SECONDS`，默认 4，`_int(..., 1, 30)` 上限 30），读多少内容取决于它跑得多快——
**机器越忙读得越少**。实测两种负载：

| 场景 | A（4 秒预算）vs C（纯字节预算） |
|---|---|
串行、低负载（40 个文件） | **40/40 完全一致**，C 不慢（0.93×）——4 秒预算平时根本用不到 |
**8 并发**（生产现状，40 个文件） | **37/40 一致；3 个被时间截断**：3601→4000、3601→4000、**1800→4000**（最严重只读到应有内容的 45%，3-gram 相似度 0.591）；C 总耗时 18.0s vs 17.3s（+4%） |
10 个 36–43MB 大文件 | C 最慢 1.05s（远低于 30s）；正文一致性 1.000（大文件对比受页缓存顺序影响，只作参考） |
纯字节预算重跑 | **8/8 逐位一致**（可复现） |

**已做（配置，无需改代码）**：`SJFX_LP_PREVIEW_SECONDS=30`（该变量的上限就是 30）。
实测最慢单文件 10.16s，30 秒有 3× 余量 → 正常文件再不会被截断，同时保留一个安全网兜住
病态文件（解析卡死、网络挂载抖动）。生效后 worker 环境里五个车道变量齐全。

**仍可选（需要改一行代码，属抽文规则变更）**：彻底去掉时间维度（`Budget.check()` 只看字节上限），
拿到 100% 可复现；代价是失去"卡死时 4 秒收手"的兜底（可保留一个很宽的硬上限，如 120s）。
这一步会改变现有目录的生成结果，**需要用户明确同意后再做**。

**影响范围要说清**：同一次构建内每个文件只预览一次就落库，目录自洽——所以这不是"目录质量变差"；
受影响的是**跨重建的可复现性**：同一份重 PDF 在不同负载下可能抽到不同的一页（最坏情况差 55% 正文），
边界文件的归属可能因此变化。提高预算后这个窗口被大幅收窄。

### 13. 嵌入搬到 GPU（2026-09-20 已上线）：把最大的一块从 7.5 小时压到 12 分钟

**为什么是这一步**：实测嵌入在 CPU 上要 **0.906 核秒/文件 × 21 万 = 53 核小时**（8 物理核上 7.5 小时），
是 100GB 预算里最大的一块；而它已经把 CPU 用到 7/8 核，**参数层面无解**（服务端 4 线程 → 8 线程
只快 7% 却多烧 1.7× CPU）。搬到 GPU 是唯一出路。

**实测数据（本机可复现）**

| 项 | 结果 |
|---|---|
GPU 嵌入吞吐（HTTP API，批 16） | **236 文件/秒**；并发 2 路客户端 **284 文件/秒**（CPU：7.0） |
折算 21 万文件 | **12.3 分钟**（CPU：7.5 小时）→ **36×** |
常驻显存（fp16 + CUDA 上下文） | **501 MiB**（空闲 1,165 MiB） |
最大压力（13,000 token 提示词 × 2 路并发 + 嵌入跑满） | **全程最低空闲 350 MiB，0 次 OOM，0 次请求失败** |
压力为何不影响显存 | vLLM 启动时按 `gpu-memory-utilization=0.94` **一次性预分配**权重+KV 池，运行时不再要显存；e5-small 激活是常数级 |
与 Qwen3.6 的干扰 | 嵌入跑满时 Qwen **65.5 → 33.5 token/秒（−49%）**，但只持续约 12 分钟 → 折算到几小时的命名里损失 **<0.1%**；停止后完全恢复（65.07） |
向量一致性（GPU fp16 vs 现有 CPU fp32） | 元素最大差 **1.01e-04**、余弦最小 0.99999976、超过 1e-3 的 **0/512** → 是分组判别区间（0.1）的 **0.101%** |
GPU fp32 对照 | 差 1.43e-07（更准），但常驻 626 MB → 最大压力下余量只剩 ~150 MiB，**反而不安全**。故选 **fp16** |

**三道服务端守卫**（用户要求"保证安全"）
1. **启动守卫**：空闲显存 < `SJFX_EMBED_MIN_FREE_MIB=600` 就不加载，每 10s 重试、10 分钟仍不够则
   **退出而不占显存**（宁可不启动，也不把同卡的 27B 挤到 OOM）。
2. **批次守卫**：每次前向前查空闲显存，低于 `SJFX_EMBED_FLOOR_MIB=150` 先等 5 秒，等不到返回 **503**。
3. **OOM 兜底**：捕获 CUDA OOM → 清缓存 → 503；服务自身不崩，vLLM 不受影响（进程间显存互不侵占）。

**第四道守卫在应用侧：自动回退 CPU**（`FallbackEmbeddingClient`，本次新增）
- 主端点 8005 失败 → 记 `warning`（**不静默**）→ 改用备端点 8004（CPU），只是慢、不会停；
- 为什么必须有：守卫一触发若没有回退，嵌入车道就停摆 → 文件拿不到向量 → 落进"未能识别内容"桶，
  那是**质量事故**；有回退则没有这个问题；
- 未配置 `SJFX_LP_EMBED_FALLBACK_URL` 时行为与改造前完全一致（零风险默认）。

**守卫演练（真实停服务实测）**：停掉 8005 → 客户端自动回退 8004，64 条 10.28s 拿回向量
（6.2 文件/秒 = CPU 速度），与 GPU 结果差 **9.97e-05**（正是 fp16/fp32 的差），日志留下
`embedding primary failed (... Connection refused); falling back to http://127.0.0.1:8004/v1`；
恢复 8005 后三服务全健康、显存归还。

**部署形态**

| 端口 | 服务 | 角色 |
|---|---|---|
8001 | vLLM Qwen3.6-27B | **完全不动** |
**8005** | **GPU 嵌入 sidecar**（`sjfx-embed-gpu.service`，fp16，批 16，准入 2） | **新增，主端点** |
8004 | CPU 嵌入服务（`sjfx-vllm-embed-v2.service`） | **原样保留** = 回退端点 |

- sidecar 用带 CUDA 的 `sjfx-vllm-local` venv（CPU 那个 venv 是 torch+cpu，跑不了 GPU）；
- unit 带 `Nice=5`（CPU 让路）、`After=sjfx-vllm.service`（开机顺序：先 vLLM 再嵌入）、
  `Restart=on-failure`、`MemoryMax=8G`，已 `enable`（开机自启）；
- 只切换了 **large_package_worker** 的启动行（`VLLM_EMBED_BASE_URL=…8005` +
  `SJFX_LP_EMBED_FALLBACK_URL=…8004`）；`app.py` / `worker.py` 仍用 CPU 服务，不替它们做主。

**回滚**（两步，都有备份）
```
# ① 流水线切回 CPU 嵌入：删掉重启脚本里那两行（备份在 .codex-backups/gpu-embed-switch-*/）
# ② 停掉 sidecar：systemctl --user disable --now sjfx-embed-gpu
```

**对 100GB 预算的影响**：文件车道的 CPU 工作量从 61–73 核小时降到 **8–20 核小时**（只剩预览）；
嵌入本身 12 分钟、对命名的干扰损失 <0.1%。**1 个 100GB 大包 ≈ 3.5–4 小时；10 个包 ≈ 4.5–6 小时**——
瓶颈从"嵌入"变成"预览（CPU）与命名（GPU，取决于分包数）"。

### 14. 「每条目一个主题」改修（2026-09-20，已上线）

**用户口径**：一个目录条目里的文件必须是同一类事物；两个互不相干的主题塞在一条里，**这条本身就不该存在**——
不是名字没起好，而是该拆开、各自独立、各自有名字。（允许"一个说得清的组织理由"，如"都是名字里含 Newton 的条目"。）

**先诊断（今天新跑的包 `48db486cf0a0`：8,178 文件 / 159 组，实测）**

| 现象 | 数字 | 根因 |
|---|---|---|
该拆没拆 | **138 次 `reason=no-outliers`**（模型答"没有异类"）；而它给"保险公司、自然保护区与人物传记的混合条目"写的描述是"**毫无关联**…**缺乏共同研究主题**，需人工审查" | **问法错了**：只问"谁不属于本组"，模型会先顺着"概括共同主题"的要求把名字凑出来，再回答"谁不属于这个名字"，于是几乎总说"没有"。信息在 description 里，我们没接 |
该合没合 | **28 组（18%）是同一主题被切成多条**，其中 **9 组完全同名**（「联合国安理会决议文本及国际安全事务记录」×4 …） | 合并车道两道闸门：① 候选要求 `needs_review=0`，而该包 **88/155 条带复核标记 → 57% 进不了候选池**（9 组同名里 6 组全带）；② 有排队任务就静默早退 |
9 条假状态名 | 「证据不足（待补充内容）」×9（共 549 个成员） | 校验器只看**被引用证据字符数 <120** 就丢掉模型给的名字——而那些组的描述明明写着具体主题 |

**A/B（零风险，82 个真实组，用用户的 52 组标注 + 30 个未标注对照）**

| 规则 | 误拆率 | 召回 | 条目净增 |
|---|---|---|---|
R1 纯模型判断 | 23.3% ✗ | 44.4% | +45% |
R2 每子组 ≥3 且 ≥10% | 0% ✓ | **0%** ✗（小组全被拦） | +6% |
**R3 尺寸感知（≤4 成员不设下限；>4 要求每子组 ≥3 且 ≥15%）** | **4.7% ✓** | 44.4% | **+12% ← 采纳** |

**一个重要的口径发现**：逐条人工核对"模型判 mixed 但用户标不该拆"的 10 个组，**约 7 个模型是对的**
（例如「中国国家级开发区…」里混进了日本行政区划、法国能源公司；「可信执行环境…」里混进了大模型缓存与智能手术室）。
原因是盲评表问的是"**名称是否概括了成员讲的事**"——一个诚实的"杂项资料"名字在那张表上会得"切合"，
但它**仍然是一个混合条目**。所以 **"切合" ≠ "不该拆"**，召回这个数字偏保守有相当一部分是标签噪声。

**四处改动**

| # | 改动 | 关键点 |
|---|---|---|
**a** | 命名调用新增结构化字段 `purity`（same/mixed/unsure）+ `subtopics`（子主题名 + 成员编号）；`VERSION` 7→8 | 用**结构化字段**而不是关键词匹配——后者才是"只针对一个包"的写法。升 VERSION 是必须的：digest 含 VERSION 而不含提示词文本，不升则旧缓存继续命中旧问法 |
**b** | `split_into_subtopics()`：按子主题建真实分组，**复用模型给的名字**（零额外调用），needs_review=1 | 尺寸感知守卫 + 预算 `lp_leaf_splits` + 待归并桶兜底 + 接受/拒绝原因日志；子主题拆分受 **`SJFX_LP_LEAF_SPLIT_SUBTOPICS=0`** 控制（回滚开关，默认开）。**注意**：`SJFX_LP_LEAF_SPLIT_NAMED` 只管"异类是否单独成组"，关不掉子主题拆分——本文档早期版本把两者写混了 |
**c** | `merge_identical_names()`：**同名叶子确定性合并**（零模型调用，排除诊断状态名，受 `effective_group_max` 约束）；合并候选去掉 `needs_review=0`；早退改为**留痕** | 同名是"同一主题"最强的证据，不该等模型判 |
**d** | 「证据不足」放宽：引用证据短**不再丢掉模型给的名字**，只标 needs_review + `naming_status='thin_evidence'`；只有引用证据一个字都没有时才退化成状态名 | |

**已上线参数**：`SJFX_LP_LEAF_SPLIT_SUBTOPICS` 默认即为开（无需写进重启脚本）；
`SJFX_LP_LEAF_SPLIT_NAMED` 默认 0 ＝ "异类不成组"，与第③项的取向一致。

**测试**：`test_catalog_evidence_quality.py` 116 条通过（新增 15 条：purity 解析 5 条、尺寸守卫 4 条、
